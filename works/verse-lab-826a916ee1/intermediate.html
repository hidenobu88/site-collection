01中級のキモ

Verse最大の発明「失敗(Failure)」という考え方

多くのプログラミング言語では、「うまくいかなかったこと」は例外(エラー)として扱われ、 プログラムが止まったり、けたたましい警告が出たりします。ですがVerseは違います。 Verseでは「うまくいかなかったこと」は異常事態ではなく、ごくふつうの結果のひとつとして扱われます。

たとえ話でわかる「失敗」

玄関の鍵を思い浮かべてください。ポケットの中にたくさんの鍵があって、ひとつずつ鍵穴に試していくとします。 鍵が回れば「成功」、回らなければ「失敗」。回らなかったからといって、家が爆発したりサイレンが鳴ったりはしませんよね。 ただ「あ、これじゃなかった」と、次の鍵を試すだけです。

Verseの「失敗」もこれと同じ感覚です。式(コード)を実行してみて、「値が出てくる(成功)」か「何も出てこない(失敗)」かのどちらか。 それだけのことであり、プログラムが壊れたわけではありません。

verse
42       # つねに成功する式。値は 42
false?   # つねに失敗する式(?は「クエリ演算子」)
true?    # つねに成功する式

クエリ演算子?は、値を「失敗する可能性のある式」に変換する道具です。配列の範囲外アクセスや、 マップに存在しないキーでの検索なども、実は自然に「失敗しうる式」になっています。

😵 他の言語でありがちな考え方
try {
  value = riskyOperation()
} catch (error) {
  // エラー処理...
}
✅ Verseの考え方
if (Value := RiskyOperation[]):
    # 成功したときだけここが動く
else:
    # 失敗した(鍵が回らなかった)だけ
🧠
この考え方がなぜ優れているのか

「検証(チェック)」と「実行」を1つの式で同時に行えるため、コードの意図がとても明確になり、うっかりチェックを忘れるバグが激減します。この章の考え方は、これから先すべての中級・上級の内容の土台になります。

関数自身が「失敗するかもしれない」ことを宣言するときは、<decides>という目印(エフェクト)を付けます。

verse
ValidateAge(Age : int)<decides> : int =
    Age >= 0        # 0未満なら、ここで失敗して終わり
    Age <= 150       # 150より大きくても失敗
    Age               # すべて通過したら Age を返して成功

比較演算子は、この「決定コンテキスト」の中では「左の値を返すか、失敗するか」という2択の道具として働きます。エフェクトについては上級編・第1章でさらに詳しく扱います。

02中級のキモ

Optional型(?T) ── 福袋のたとえ

「値があるかもしれないし、ないかもしれない」というデータを表すための型がOptional(オプション型)です。 書き方は、型の前に?を付けて?intや?stringのように表します。

たとえ話でわかる Optional

福袋を思い出してください。買うまで中身はわかりません。「何か入っている福袋」もあれば、「空の福袋」もある、という状態です。 Optional型の変数は、まさにこの福袋そのもの。開けてみるまで、中に値があるかどうかわかりません。

verse
HasPrize : ?int = option{42}   # 中身入りの福袋(42が入っている)
Empty    : ?int = false        # 空の福袋

# ? 演算子で袋を「開けて」中身を取り出す(失敗する可能性がある操作)
if (Prize := HasPrize?):
    Print("あたり! {Prize}")
else:
    Print("今回ははずれ")

# option{式} は、式が失敗したら自動的に「空の福袋」に変換してくれる
Result := option{RiskyComputation[]}
🎁
Optionalと「失敗」の関係

実はOptional型は、前の章で学んだ「失敗」という考え方を「値」として持ち運べる形にしたものです。?で袋を開ける操作そのものが「失敗しうる式」になっています。

✏️ ミニクイズ
Q. ?int型の変数を「開けて」中身を取り出すために使う記号はどれ?
正解はB。?は「クエリ演算子」と呼ばれ、Optionalな福袋を開けて中身を取り出す(あるいは失敗する)操作に使います。
03中級のキモ

if式の複数条件チェーン

「失敗」の考え方が本当に輝くのは、if式の中です。カンマ区切りで複数の失敗しうる式を並べると、 「前の式が成功したら、次の式に進む」という階段のような処理を、驚くほど短く書けます。

たとえ話でわかる 条件チェーン

障害物競走を思い浮かべてください。1つ目のハードルを飛び越えられた選手だけが、2つ目のハードルに挑戦できます。 1つでも引っかかったら、そこでコースアウト(else行き)。ifのカンマは、まさにこのハードルの連なりです。

verse
if (Player := GetPlayerByName[Name],      # ハードル1: プレイヤーが見つかるか
    Score  := GetPlayerScore[Player],      # ハードル2: スコアが取得できるか
    Score  > 100):                        # ハードル3: 100点より上か
    Print("ハイスコア達成者です!")
else:
    Print("条件を満たしませんでした")

すごいのは、2つ目のハードル(GetPlayerScore[Player])が、1つ目のハードルで手に入れたPlayerという結果を そのまま使えるところです。ひとつの流れるような文章のように「検索して → その結果を使って検索して → その結果を判定する」と書けます。

04ふつう

for式でふるいにかける

for式にも、失敗しうる式をカンマで追加できます。すると、条件に合わなかった要素だけを自動でスキップする 「ふるい分け(フィルタリング)」ができるようになります。

たとえ話でわかる for のふるい

砂場で砂金探しをするとき、ザル(ふるい)を使いますよね。粗い砂利はザルの外に落ちていき、金色に光る小さな粒だけが残ります。 forのカンマ以降の条件は、まさにこの「ザル」の役目を果たします。

verse
Inventory := array{"棒", "鉄の剣", "パン", "光る盾"}

# 「武器」と判定でき、なおかつダメージが50より大きい物だけを残す
for (ItemName : Inventory, IsWeapon[ItemName], Damage := GetDamage[ItemName], Damage > 50):
    Print("強力な武器を発見: {ItemName}")
🎯
for は実は「値を作る式」でもある

forの結果を変数に代入すると、条件を通過した要素だけを集めた新しい配列が返ってきます。これは初級編の「すべては式」という考え方が、ここでも活きている良い例です。

05ふつう

and / or / not とフォールバック

失敗という考え方は、論理演算子and or notとも自然に噛み合います。

たとえ話でわかる or のフォールバック

高校受験の第一志望・第二志望・第三志望を思い出してください。「第一志望がダメだったら、第二志望を試す。それもダメなら第三志望」。 orでつなげた式は、まさにこの「志望校フォールバック」です。最初に成功したものが、そのまま採用されます。

verse
# 一番手に入れたいメイン武器がダメなら、サブ、それもダメなら初期装備
Weapon := PrimaryWeapon[] or SecondaryWeapon[] or DefaultWeapon?

# 経路探索の例: 一番効率のいい方法から順に試す
FindPath(Start : location, End : location)<decides> : path =
    DirectPath[Start, End] or
    PathAroundObstacles[Start, End] or
    ComplexPathfinding[Start, End]
演算子たとえ成立する条件
and入試の必須科目すべて合格両方とも成功したときだけ成功
or志望校フォールバックどちらか一方でも成功すればOK
not「不合格ではない」への言い換え成功⇔失敗をひっくり返す
06ふつう

構造体(struct) ── データのカード

いくつかのデータをひとまとめにして、名前をつけて扱いたいときに使うのが構造体(struct)です。 構造体はメソッドを持たない、純粋な「データの入れ物」です。

たとえ話でわかる struct

トレーディングカードゲームの「ステータスカード」を思い浮かべてください。攻撃力・防御力・HPが書かれたカードです。 このカードを友達に見せて「コピーしていいよ」と渡すと、相手はまったく同じ内容の"別のカード"を手に入れます。 あなたのカードに後から書き込みをしても、友達のコピーには一切影響しません。構造体はこの「コピーされるカード」の性質を持っています。

verse
player_stats := struct:
    Level : int = 1
    HP    : int = 100
    Attack : int = 10

# フィールド名を指定してインスタンスを作る(名前付き引数のような書き方)
MyStats := player_stats{Level := 5, HP := 150}
DefaultStats := player_stats{}          # すべてデフォルト値のまま

# コピーの性質を確認する
var Original : player_stats = player_stats{Level := 5}
var Copy : player_stats = Original       # ここで「深いコピー」が発生
set Copy.Level = 10
Print(Original.Level)                     # → 5 (Originalは変化しない!)
📝
構造体のフィールドはデフォルトで公開&不変

構造体のフィールドは、特別な指定がなければ「誰からでも読める」「作られた後は書き換えられない」状態です。書き換えたい場合はvar付きの変数に構造体そのものを入れ、丸ごと新しいコピーでsetする必要があります。

構造体はジェネリック(型パラメータ)にも対応しています。「どんな型でも包める箱」を1つ定義できます。

verse
wrapper(t : type) := struct:
    Value : t

IntWrapped    := wrapper(int){Value := 42}
StringWrapped := wrapper(string){Value := "こんにちは"}
07ふつう

列挙型(enum) ── open と closed

「取りうる値がいくつかに決まっている」データを表すのが列挙型(enum)です。 マジックナンバー(意味のわからない謎の数字)を避けられる、とても大切な道具です。

たとえ話でわかる enum の open / closed

信号機の色(赤・黄・青)は、これから先も絶対に増えません。これがenum<closed>(閉じた列挙型)です。すべてのパターンを安心して網羅できます。
一方で、「これから追加されるかもしれない職業リスト」は、将来ゲームアップデートで新しい職業が増えるかもしれません。これがenum<open>(開いた列挙型)です。「まだ知らない未来の値」に備えて、必ず「その他」の受け皿を用意しておく必要があります。

verse
day_of_week := enum<closed>:   # デフォルトは closed。もう増えない前提
    Monday
    Tuesday
    Wednesday

weapon_type := enum<open>:      # 将来アップデートで追加されるかもしれない
    Sword
    Bow

# パターンマッチング(case式)
DescribeWeapon(W : weapon_type) : string =
    case (W):
        weapon_type.Sword => "白兵戦向きの武器"
        weapon_type.Bow   => "遠距離向きの武器"
        _                 => "未知の新武器"   # openなので必須の受け皿
💡
型と値を混同しない

weapon_type自体は「型」で、weapon_type.Swordが実際の「値」です。「箱の設計図」と「箱の中身」くらい別物、と覚えておきましょう。

08中級のキモ

クラス(class)と継承

構造体が「コピーされるカード」だったのに対して、クラス(class)は挙動をあわせ持つ「実体」です。 そしてクラスには構造体にはない、決定的な違いがあります──コピーではなく「共有」されるのです。

たとえ話でわかる class(参照セマンティクス)

テレビゲームのコントローラーを2人で回し持ちしていると考えてください。コントローラーが2つあっても、操作しているキャラクターは1体だけです。 1人がキャラクターにダメージを与えれば、もう1人の画面でも同じキャラクターのHPが減っています。 クラスの変数をコピーしても、それは「同じキャラクターを指す、新しいコントローラー」が増えるだけで、キャラクター自体は増えません。

verse
character := class:
    Name : string
    var Health : int = 100

    TakeDamage(Amount : int) : void =
        set Health = Max(0, Health - Amount)

Player1 := character{Name := "ゆうた"}
Player2 := Player1            # コントローラーが増えるだけ、キャラは同じ

Player2.TakeDamage(30)
Print(Player1.Health)          # → 70 (Player1側にも影響する!)

クラスは単一継承(1つの親クラスだけ)をサポートしています。「動物 → 犬」のような家系図をコードで表現できます。

verse
entity := class:
    var Position : vector3 = vector3{}

# character は entity を「継承」している(entityの機能をすべて引き継ぐ)
character := class(entity):
    Name : string

    Move(Delta : vector3) : void =
        Print("{Name}が移動しました")

# メソッドをオーバーライド(上書き)し、親の実装も呼び出す例
base := class:
    Greet() : void = Print("私は生き物です")

derived := class(base):
    Greet<override>() : void =
        (super:)Greet()             # 親の処理も実行しつつ
        Print("その中でも、私は犬です")
✏️ ミニクイズ
Q. クラスのインスタンスを別の変数にコピーすると、何が起きる?
正解はB。クラスは「参照セマンティクス」なので、コピーしても中身は共有されたままです。これが構造体との一番の違いでしたね。
09ふつう

インターフェース(interface)

インターフェースは、「このクラスはこの機能を必ず持っています」という約束(契約)を定義するものです。

たとえ話でわかる interface

家庭用コンセントの規格を思い浮かべてください。ドライヤーだろうと掃除機だろうと炊飯器だろうと、 プラグの形(規格)さえ合っていれば、メーカーが違っても同じコンセントに挿せます。 インターフェースは、この「差込口の規格」です。中身がどんなクラスであっても、同じ規格(インターフェース)を実装していれば、同じように扱えます。

verse
# 「ダメージを受けられる」という規格(コンセントの形)を定義
damageable := interface:
    TakeDamage(Amount : int)<transacts> : void
    MaxHealth : int = 100          # デフォルト実装も持てる

# character クラスは damageable の規格を実装(プラグの形を合わせる)
character := class(damageable):
    var Health : int = 100

    TakeDamage<override>(Amount : int)<transacts> : void =
        set Health = Max(0, Health - Amount)

# 樽や壁など、character と無関係な物でも同じ規格を実装できる
barrel := class(damageable):
    var Health : int = 30
    TakeDamage<override>(Amount : int)<transacts> : void =
        set Health = Max(0, Health - Amount)

クラスは親を1つしか持てませんが(単一継承)、インターフェースはいくつでも同時に実装できます。 「ダメージを受けられる」規格と「持ち上げられる」規格を、両方同時に満たすオブジェクトも作れるということです。

🔌
名前がぶつかったら?

2つのインターフェースに同じ名前のメソッドがあるときは、(インターフェース名:)メソッド名のように「どちらの規格の話か」をはっきり書いて区別します。

10中級のキモ

コピーか、共有か ── struct と class の使い分け

ここまでの内容を整理しましょう。この違いを体に染み込ませておくと、後々のバグをかなり防げます。

構造体(struct)クラス(class)
たとえコピーされるトレーディングカード複数人で回し持つコントローラー
代入したらまったく別の複製が作られる同じ実体を指す参照が増える
メソッド持てない(データだけ)持てる
継承できない単一継承ができる
向いている場面座標、色、ステータス値など「値」そのものプレイヤー、敵キャラなど「同一性」が大事なもの
🧭
選び方の目安

「これは2つあったら"別物"として扱いたい(例: 2人のプレイヤー)」ならclass。「これは中身が同じなら"同じ値"として扱いたい(例: 同じ座標(3,4))」ならstruct、と考えるとスムーズです。

11ふつう

名前付き引数とデフォルト値

関数を呼び出すとき、引数に名前をつけて渡せる仕組みがあります。順番を気にせず、必要な項目だけを指定できます。

たとえ話でわかる 名前付き引数

ハンバーガーショップの「カスタムオーダー用紙」を思い浮かべてください。「ピクルス抜き」「チーズ増し」のように、 変えたい項目だけチェックを入れれば、それ以外は標準(デフォルト)のまま作ってもらえますよね。名前付き引数もこれと同じ感覚です。

verse
# ?を付けた引数が「名前付き引数」。デフォルト値も指定できる
Log(Message : string, ?Level : int = 1, ?Color : string = "white") : string =
    "[Lv{Level}] {Message} ({Color})"

Log("起動しました")                       # デフォルトのまま
Log("警告です", ?Level := 2)              # Levelだけカスタム(チーズ増しのように)
Log("危険!", ?Level := 3, ?Color := "red") # 複数項目カスタム
12ふつう

拡張メソッド

すでにある型(intのような組み込みの型でさえも)に、あとから新しい機能を追加できるのが拡張メソッドです。

たとえ話でわかる 拡張メソッド

スマートフォンに、あとから「バンカーリング」や「カード収納ケース」を後付けするイメージです。スマホ本体を作り直さなくても、 便利な機能を外側からペタッと追加できますよね。拡張メソッドは、既存の型に対する「便利な後付けアクセサリ」です。

verse
# int型に「2倍にする」という機能を後付けする
(N : int).Double() : int = N * 2

X := 5
Y := X.Double()          # → 10 (まるで元から備わっていた機能のように呼べる)
13やや難しい

ジェネリック関数入門

「どんな型が来ても対応できる、万能な関数」を作れる仕組みがジェネリック(型パラメータ)です。

たとえ話でわかる ジェネリック関数

空港の「万能変換プラグ」を思い浮かべてください。日本のプラグでも、アメリカのプラグでも、ヨーロッパのプラグでも挿せる、形を選ばない変換アダプターです。 ジェネリック関数は、intが来てもstringが来ても、同じロジックを適用できる「型を選ばない関数」です。

verse
# t という「型そのもの」を引数のように受け取る
Identity(X : t where t : type) : t = X

Identity(42)          # t は int になる
Identity("こんにちは")  # t は string になる

# 関数のオーバーロード: 同じ名前でも型ごとに別の処理を書ける
Process(Value : int)    : string = "整数です: {Value}"
Process(Value : float)  : string = "小数です: {Value}"
🔧
where句で条件をつける

where t : subtype(comparable)のように書くと、「どんな型でもいいわけではなく、比較できる型限定」のように制限をかけられます。工具箱の中でも「ネジ回し系だけ」のように、使える道具の範囲を絞るイメージです。

14やや難しい

サブタイピング入門 ── 型の親子関係

「Aという型は、Bという型の"仲間"として扱える」という関係をサブタイプと呼びます。

たとえ話でわかる サブタイプ

「犬は動物である」という関係を思い浮かべてください。「動物を1匹連れてきて」と言われたら、犬を連れていっても文句は言われません。 犬は動物のサブタイプ(仲間)だからです。しかし逆に「犬を1匹連れてきて」と言われた場面に、得体のしれない生き物(動物)を連れていくのはNGですよね。

verse
GetRat(X : rational) : void = Print("有理数として扱いました")

MyInt : int = -10
GetRat(MyInt)     # OK -- int は rational の「仲間(サブタイプ)」

vehicle := class:
    Speed : float = 0.0

car := class(vehicle):
    NumDoors : int = 4

sports_car := class(car):
    Turbo : logic = true

# sports_car は car の仲間、car は vehicle の仲間
# つまり sports_car は vehicle が必要な場所でも使える
🔄
型変換はいつも「はっきりと」

Verseでは「なんとなく自動で変換される」ことがありません。intからfloatへの変換でさえ、MyInt * 1.0のように意図をはっきり示す必要があります。「思っていたのと違う値になっていた」という事故を防ぐためのルールです。

15ふつう

アクセス指定子 ── 誰が見て・触れるか

クラスやモジュールの中身を「誰から見えるようにするか」を決めるのがアクセス指定子です。

たとえ話でわかる アクセス指定子

自分の家を思い浮かべてください。玄関(public)は誰でも訪ねてこられます。 日記(private)は自分しか読めません。家族専用のリビング(protected)は、家族(継承したクラス)だけが入れます。 マンションの共用施設(internal)は、同じマンション(モジュール)の住人だけが使えます。

指定子たとえ見える範囲
public玄関どこからでもアクセス可能
protected家族専用リビング自分自身と、継承した子クラスだけ
internal(既定)マンションの共用施設同じモジューノの中だけ
private自分の日記定義した直後のスコープだけ
scoped{...}特定の友人だけに見せる合鍵指定したモジュール同士だけ
verse
inventory := class:
    var Items<private> : []item = array{}   # 自分の日記(外から直接いじれない)

    AddItem<public>(NewItem : item) : void =  # 玄関(誰でも呼べる)
        set Items += array{NewItem}
16実践

実践: シンプルなインベントリシステムを作る

ここまで学んだstruct・enum・class・失敗・Optionalを組み合わせて、ゲームでおなじみの 「持ち物リスト(インベントリ)」を実際に作ってみましょう。

verse — inventory_demo.verse
# アイテムの種類。今後増える可能性があるので open にしておく
item_category := enum<open>:
    Weapon
    Potion
    Key

# 1つのアイテムを表す「カード」。値としてコピーされてよいので struct
item := struct:
    Name     : string = ""
    Category : item_category = item_category.Potion
    Count    : int = 1

# 持ち物リストそのものは「同一性」が大事なので class
inventory := class:
    var Items<private> : []item = array{}

    # 追加する。同名アイテムがあれば個数を増やす(失敗してもよい設計)
    AddItem<public>(NewItem : item) : void =
        if (ExistingIndex := Items.Find[NewItem]):
            # 見つかった場合(ここでは簡略化のため個数だけ表示)
            Print("{NewItem.Name} をすでに持っています")
        else:
            set Items += array{NewItem}
            Print("{NewItem.Name} を入手した!")

    # ポーションだけを取り出す(for式のふるい分けを活用)
    GetPotions<public>()<transacts> : []item =
        for (I : Items, I.Category = item_category.Potion):
            I

MyBag := inventory{}
MyBag.AddItem(item{Name := "伝説の剣", Category := item_category.Weapon})
MyBag.AddItem(item{Name := "薬草", Category := item_category.Potion, Count := 3})

for (P : MyBag.GetPotions()):
    Print("回復アイテム: {P.Name}")
🏗️
設計のポイントを振り返る

itemは「コピーされてよいカード」だからstruct、inventoryは「唯一無二の持ち物袋」だからclass、将来アイテム種類が増える前提だからitem_categoryはopenな列挙型にしています。それぞれ、この章で学んだ「使い分けの感覚」がそのまま活きています。
