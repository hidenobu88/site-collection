01上級のキモ

エフェクトという「成分表示ラベル」

Verseの関数には、名前・引数・戻り値の他に、もうひとつ大事な情報が書かれています。それがエフェクト(効果)です。 「この関数は、実行中に何をする可能性があるか」を、< >で囲んで宣言します。

たとえ話でわかる エフェクト

スーパーで売っているお菓子の袋の裏にある「成分表示ラベル」を思い浮かべてください。 「小麦・卵・乳成分を含みます」と書かれていれば、アレルギーがある人はひと目で避けられますよね。

Verseのエフェクトも同じ役目です。<reads>と書かれていれば「この関数はゲームの状態を読み取ります」、 <writes>なら「状態を書き換えます」と、関数の中身を1行も読まなくても、何をする関数かパッケージの外側からわかるのです。 そしてコンパイラが、この表示が嘘になっていないかを厳密にチェックしてくれます。

verse
CalculateDamage(Base : float, Mult : float)<computes> : float =
    Base * Mult                    # 何も読み書きしない、純粋な計算

GetStatus(P : player)<reads> : string =
    if (P.Health > 50.0): "元気" else "負傷中"   # 状態を読むだけ

HealPlayer(P : player, Amount : float)<transacts> : void =
    set P.Health = Min(P.Health + Amount, 100.0)  # 状態を書き換える

エフェクトには大きく3つの「家族」があります。この地図を頭に入れておくと、これから先の章がすべてつながって見えてきます。

📦

Heapファミリー

computes / reads / writes / transacts ── メモリの読み書きに関する成分表示。

🎲

Cardinalityファミリー

decides ── 「失敗するかもしれない」という成分表示。

⏳

Suspensionファミリー

suspends ── 「時間をまたいで一時停止するかもしれない」という成分表示。

02上級のキモ

computes 〜 transacts の階層

Heapファミリーの4つは、権限の強さの階段になっています。

たとえ話でわかる 権限の階段

図書館の利用証を思い浮かべてください。「館内閲覧のみ」証では本を読むだけ。「貸出可」証があれば本を持ち帰って書き込みもできる──というように、 できることの範囲が段階的に広がっていきますよね。

エフェクトたとえできること
<computes>電卓を使うだけ純粋な計算のみ。何も読み書きしない
<reads>館内閲覧のみの利用証状態の読み取りが許可される
<writes>書き込み許可の利用証状態の変更が許可される
<transacts>(既定)フル権限の利用証読み取り・書き込み・確保すべて許可

重要なのは、この階段が「制限が少ない関数は、制限が多い場所でも代わりに使える」というサブタイピングの関係にあることです。 「純粋な計算しかしない関数」は、「読み取りをしてもよい」という場所に渡しても何の問題もありませんよね。

verse
PureAdd(X : int)<computes> : int = X + 1

# 「computes以上の権限を持つ関数ならOK」という場所にも、
# 一番権限の弱い computes 関数を渡せる
F : type{_(:int)<computes><decides> : int} = PureAdd   # 有効
🚫
ルール: 同じ指定子を2つ書けない

<computes><computes>のような重複はエラーになります。また<suspends>と<decides>は組み合わせられません。「一時停止するかもしれない」と「失敗するかもしれない」は、Verseでは意図的に別の枠組みとして扱われているためです。

03ふつう

decides エフェクトと失敗の伝播

中級編で学んだ「失敗」の考え方は、<decides>というエフェクトとして関数の成分表示に現れます。 そしてこの成分表示は、まるでバケツリレーのように呼び出し元へ伝わっていきます。

verse
# AttemptPurchase は自分自身が「失敗するかもしれない」ので <decides> を宣言
AttemptPurchase(Cost : int)<transacts><decides> : void =
    set PlayerGold = PlayerGold - Cost   # 一旦、暫定的に引いてみる
    PlayerGold >= 0                       # マイナスならここで失敗

AttemptPurchaseを呼び出す側の関数もまた、この失敗の可能性を受け止める(<decides>を宣言するか、 ifで失敗コンテキストに包む)必要があります。成分表示が正直に連鎖していくことで、 「どこかで失敗が握りつぶされて、気づかないバグになる」事故を未然に防いでいます。

⚠️
「失敗」と「実行時エラー」は別物

Err("メッセージ")で発生させる実行時エラーは、鍵が回らなかっただけの「失敗」とは違い、回復不可能な致命的な異常を表します。コールスタックを伝って処理が強制終了するため、「本当に続行不可能なとき」だけに使うべき、最後の手段です。

04上級のキモ

suspends と非同期処理の基本

普通の関数は「一瞬(1フレーム)で処理が終わる」ことが前提です。しかし「3秒待つ」「アニメーションが終わるまで待つ」といった、 時間をまたぐ処理をしたい関数には、<suspends>という成分表示が必要です。

たとえ話でわかる suspends

電子レンジでお弁当を温めているところを思い浮かべてください。「温め始める」というボタンを押した瞬間に処理は終わりません。 チンと鳴るまでの間、その場に立ち止まって待つ必要があります。<suspends>が付いた関数は、 この「電子レンジの前で待っている時間」を表現できる関数、というわけです。

verse
PlaySequence()<suspends> : void =
    PlayAnimation(Dance)
    Sleep(2.0)                  # 2秒間、実行を一時停止する
    PlaySound(FanfareSound)
📡
suspendsも伝播する

<decides>と同じように、<suspends>な関数を呼び出す関数自身も<suspends>を宣言する必要があります。「電子レンジの前で待つ人を呼びに行った人も、結局は一緒に待つことになる」というわけです。

05上級のキモ

並行処理 ① sync ── 全員そろうまで待つ

Verseの並行処理は「構造化並行処理」という設計で、並行タスクの寿命が、必ずコードの見た目のブロックに収まるようになっています。 4つの主な仲間、sync / race / rush / branchと、少し特殊なspawnを順番に見ていきましょう。まずはsyncです。

たとえ話でわかる sync

運動会の「大縄跳びリレー」を思い浮かべてください。すべてのチームが縄跳びを跳び終えるまで、次の種目には進めません。 全員がそろうまで、全体が待つ──これがsyncです。

verse
Results := sync:
    LoadTexture()
    LoadSound()
    LoadModel()

# 3つすべてのロードが完了してから、ここに到達する
ProcessData(Results(0), Results(1), Results(2))
🎮
向いている場面

ゲーム開始時に「テクスチャ・サウンド・モデル」など、複数の準備を同時並行で進め、すべてが終わってから次に進みたいときに最適です。1つずつ順番に待つより、ずっと速く準備が終わります。

06上級のキモ

並行処理 ② race ── 早い者勝ち

たとえ話でわかる race

文字通り「徒競走」です。3人が同時にヨーイドンでスタートし、1着になった選手が決まった瞬間、まだ走っている他の選手たちはそこで棄権させられます。 raceは、最初に完了した処理の結果だけを受け取り、残りは自動的にキャンセルされます。

verse
Winner := race:
    SlowOperation()
    FastOperation()
    MediumOperation()

# FastOperationの結果を受け取り、他の2つは自動キャンセルされている
⏱️
タイムアウト処理の定番パターン

raceは「本来やりたい処理」と「制限時間のSleep」を競わせることで、タイムアウト機能を簡単に実装できます。制限時間の方が先にゴールしたら、本来の処理は自動的に打ち切られます。

07やや難しい

並行処理 ③ rush ── 一番乗りを見ながら、他も走らせ続ける

たとえ話でわかる rush

宿題と部活の朝練を同時に進める学生を想像してください。「とりあえず宿題が終わった時点で一旦チェックを受けるけれど、 朝練のランニングメニューはそのまま続けさせる」──rushは、最初の完了は教えてくれつつも、 raceと違って残りのタスクをキャンセルせず、裏側で走らせ続けます。

verse
FirstResult := rush:
    LongBackgroundTask()   # 時間がかかるが、最後までやり切ってほしい
    QuickCheck()            # すぐ終わる確認作業

# QuickCheckの結果を先に受け取れるが、LongBackgroundTaskは裏で継続中
💡
向いている場面

「素早い応答性がほしいけれど、時間のかかる処理も最後までちゃんと終わらせたい」という場面。ただしループの本体で直接使うことはできない、という制約があります。

08やや難しい

並行処理 ④ branch と spawn ── バックグラウンド任務

たとえ話でわかる branch と spawn

branchは「打ち上げ花火」です。導火線に火をつけたら、その場で結果を見届けずに次の作業に進みます。 花火は勝手に打ち上がりますが、その場面(スコープ)が終わったら、花火自体も自動的に片付けられます。
spawnは「独立した長期プロジェクト」です。担当者(呼び出し元の処理)がすでに退社していても、 プロジェクト自体はスコープをまたいで生き続けます。

verse
# branch: 花火を打ち上げて、その場はすぐ先に進む
branch:
    PlayBackgroundEffect()
    UpdateSystemAsync()
# ここにはすぐ到達する(バックグラウンドはまだ実行中)

# spawn: スコープを超えて独立して生き続けるタスクを作る
BackgroundTask : task(int) = spawn{ LongRunningWork() }

# task型が持つ操作
BackgroundTask.Cancel()          # キャンセルを依頼する
Result : int = BackgroundTask.Await()   # 完了を待って結果を受け取る
キーワードたとえいつ使う
sync大縄跳びリレー(全員待つ)複数の初期化処理をまとめて待ちたいとき
race徒競走(1着以外は失格)タイムアウトなど、最速の結果だけ欲しいとき
rush宿題と朝練を並行(両方やり切る)速い応答と完全な処理、両方ほしいとき
branch打ち上げ花火(発射して次へ)結果を待たずに背景処理をしたいとき
spawn独立した長期プロジェクトスコープをまたいで生き続く常駐処理
✏️ ミニクイズ
Q. 「制限時間3秒以内に敵を倒せなければタイムアウト」を実装したい。どのキーワードが最適?
正解はB。「敵を倒す処理」と「3秒のSleep」をraceで競わせれば、先にゴールした方の結果だけが採用される、典型的なタイムアウトパターンになります。
09やや難しい

協調的キャンセル ── 律儀な職人のように

raceで負けたタスクや、Cancel()を呼ばれたタスクは、実はその瞬間に即座には止まりません。

たとえ話でわかる 協調的キャンセル

職人さんに「もう作業をやめてください」と伝えても、ノコギリを動かしている途中でいきなり手を止めたりはしませんよね。 「キリのいいところ(次の作業の切れ目)まで来たら、やめます」と応じるのが自然です。 Verseのキャンセルもこれと同じ「協調的」な仕組みです。タスクは、あらかじめ決められた「中断ポイント」 (Sleepや関数呼び出しなど)に来たときだけ、「あ、キャンセルされてる」と気づいて止まります。

verse
ResponsiveLoop()<suspends> : void =
    for (I := 0..10000):
        ExpensiveOperation(I)
        Sleep(0.0)          # 中断ポイント。ここでキャンセル信号をチェックする
🪚
中断ポイントがないと、止まれない

もし重い処理の中にSleepや関数呼び出しなどの中断ポイントが一切なければ、キャンセルを頼んでもすぐには反応してくれません。時間のかかるループには、こまめに中断ポイントを挟むのが良い設計です。また、親タスクがキャンセルされると、その子タスクにもキャンセルが自動的に伝わっていきます。

10ふつう

defer とリソース管理

「使ったら必ず片付ける」処理を、忘れずに実行してくれるのがdeferです。

たとえ話でわかる defer

学校の「教室の電気を消す当番」のようなものです。用事が急に入って教室を飛び出すことになっても(キャンセルや早期リターンが起きても)、 deferで予約しておいた「電気を消す」という後片付けは、教室を出るタイミングで必ず実行されます。

verse
ProcessWithTimeout()<suspends> : void =
    race:
        block:
            Resource := AcquireResource()
            defer:
                ReleaseResource(Resource)   # 途中でキャンセルされても必ず実行
            LongTask(Resource)
        block:
            Sleep(10.0)                     # 10秒経ったらタイムアウト
11上級のキモ

トランザクションとロールバック

<transacts>エフェクトを持つ関数の中で行った変更は、もし途中で失敗したら、まるで最初から何も起きなかったかのように取り消されます。

たとえ話でわかる トランザクション

ゲームで強敵に挑む前に、必ずセーブしてから挑みますよね。もし負けてしまったら、ロードしてやり直せば、挑戦前の状態にきれいに巻き戻ります。 <transacts>の中身は、この「セーブ→挑戦→失敗したら自動ロード」を、Verseが裏側で自動的にやってくれる仕組みです。

verse
AttemptPurchase(Cost : int)<transacts><decides> : void =
    set PlayerGold = PlayerGold - Cost   # 暫定的に所持金を減らす(仮の変更)
    PlayerGold >= 0                       # マイナスになったら…

# ↑ もし失敗したら、PlayerGoldは「減らす前」の状態に自動で巻き戻る。
#   「所持金だけ減って、商品は手に入らない」という中途半端な事故が起きない。
🛡️
なぜこれが重要なのか

他の多くの言語では「途中まで処理が進んだ状態で例外が起きて、データが中途半端に壊れる」というバグがよく起きます。Verseはこの問題を、言語の仕組みそのもので根本から解決しています。これは「投機的実行(Speculative Execution)」とも呼ばれます。

12上級のキモ

Live Variables ── 自動で計算し直される変数

普通の変数は、一度計算したら値は固定です。しかしLive Variablesを使うと、 「元になる値が変わったら、自動的に再計算される変数」を作れます。

たとえ話でわかる Live Variables

表計算ソフト(エクセル)のセルを思い浮かべてください。B1セルに「=A1+1」という数式を入れておくと、 A1の値を変えるたびに、B1は手で計算し直さなくても自動で更新されますよね。 Live Variablesは、まさにこの「数式が入ったセル」をプログラムの変数として使えるようにしたものです。

verse
var X : int = 0
var Y : int = 0

set live X = Y + 1   # X は Y を「数式」として追いかけるようになる
set Y = 5
Print(X)               # → 6 (Yが変わると、Xも自動で追従する)

宣言の仕方にはいくつかバリエーションがあります。

verse
var live X : int = Exp     # 可変なリアクティブ変数として宣言
live Y : int = Exp          # 不変なリアクティブ変数として宣言
set live X = Exp            # 既存の変数にリアクティブ性を後付け

ゲームでよくある「上限・下限のあるHPバー」も、Live Variablesで自然に表現できます。

verse
clamp := class:
    var Lower : int = 0
    var Upper : int = 100
    Evaluate(Value : int)<reads> : int =
        if (Value < Upper) then
            if (Value > Lower) then Value else Lower
        else Upper

# Health に値を入れると、自動的に0〜100の範囲に丸められる
var BaseHealth->Health : clamp.Evaluate = 50
set Health = 120     # BaseHealthは120になるが、Health自体は100で頭打ち
📏
依存関係は実行時に決まる

「数式(条件式)がどの変数に依存しているか」は、コンパイル時ではなく実行時に動的に決まります。if (Z > 0) then X else Yという数式なら、Zの値によって「Xを見張る」か「Yを見張る」かが切り替わります。またこの数式に<writes>エフェクトを持たせることはできません──あくまで「見張って再計算するだけ」の存在だからです。

13やや難しい

await / upon / when / batch

Live Variablesと組み合わせて使う、時間・条件に関する4つの便利な仲間を紹介します。

⏰

await

目覚まし時計のように、条件が満たされるまでその場で待ち続け、満たされたら1回だけ先に進みます。

🚨

upon

ホームセキュリティのセンサーのように、条件が最初にtrueになった瞬間、1回だけコードを実行します。

📹

when

常時監視カメラのように、条件がtrueである間、変化のたびに何度でもコードを実行し続けます。

🧾

batch

スーパーのレジのように、複数の変更をまとめてから、最後に1回だけ会計(通知)します。

verse
# await: Xが変化するまで待って、1回だけ先に進む
await{X <> OldX}
Print("Xが変わった: {X}")

# upon: HPが0以下になった瞬間、1回だけ死亡フラグを立てる
upon(Health <= 0):
    set IsDead = true

# when: スコアが変わるたびに、表示用の値を更新し続ける
when(Score):
    set DisplayedScore = Score

# batch: XとYをまとめて更新し、途中経過では反応させない
batch:
    set X = 2
    set Y = 10
# ここでようやく、リアクティブな反応がまとめて1回発生する
14やや難しい

Refinement Types ── 値の範囲を絞る鋳型

型に「この範囲の値しか許さない」という追加ルールを持たせられるのがRefinement Types(改良型)です。

たとえ話でわかる Refinement Types

金属加工の「鋳型(いがた)」を思い浮かべてください。溶けた金属を流し込んでも、鋳型の形からはみ出た部分は作れません。 Refinement Typesは、まさに「この範囲の値しか通さない鋳型」を型として定義できる機能です。

verse
# 0.0以上1.0以下の値しか受け付けない「鋳型」
percent := type{_X : float where 0.0 <= _X, _X <= 1.0}

Opacity : percent = 0.5     # OK -- 鋳型の範囲内
# BadOpacity : percent = 1.5  # コンパイルは通っても実行時に失敗する
📐
制約に書けるのは「リテラル」だけ

鋳型のルールに書けるのは0.0や1.0のような、その場に直接書かれた値(リテラル)だけです。変数や関数呼び出しを条件に混ぜることはできません。

15やや難しい

メタタイプ ── 「型そのもの」を値として扱う

Verseでは型そのものを値として持ち運べます(type型)。これをさらに便利に使うための3つの道具があります。

たとえ話でわかる メタタイプ

図鑑の「動物」のページを思い浮かべてください。subtype(animal)は「動物図鑑に載っているすべての種類(犬・猫・鳥…)」を指す言葉です。 しかし「動物」という抽象的な概念そのものは、実際に1匹連れてくることはできません。
一方concrete_subtype(animal)は、「実際にペットショップで購入できる、具体的な種類」だけに絞り込んだリストです。

verse
# subtype(T): Tの仲間である「型」を値として表す
AnimalType : subtype(animal) = dog

# concrete_subtype(T): 実際にインスタンス化できる具体的な型
EntityType : concrete_subtype(entity) = player
NewEntity := EntityType{}          # 実際に「作れる」

# castable_subtype(T): <castable>マーク付きの型限定
ComponentType : castable_subtype(component) = physics_component
🧬
何がうれしいのか

「実行時に、どの敵キャラを生成するかを動的に切り替えたい」といったケースで活躍します。コンパイル時の型安全性を保ったまま、実行時のポリモーフィズム(多態性)を実現できるのがメタタイプの強みです。

16ふつう

モジュールとパス

コードが大きくなってくると、整理整頓が欠かせません。Verseではフォルダ構造そのものが、そのままモジュール構造になります。

たとえ話でわかる モジュール

学校の「教室配置図」を思い浮かべてください。「3階の3組の教室」のように、建物の物理的な位置がそのまま所属を表しますよね。 Verseのモジュールも同じで、フォルダを作るだけで、それがそのまま1つのモジュール(名前空間)になります。 同じフォルダの中の.verseファイルは、全部「同じ教室の生徒」として扱われます。

verse
# モジュールの定義(コロン構文)
GameConfig := module:
    MaxPlayers<public> : int = 100

# using で他のモジュールを読み込む(ファイルの先頭に書く)
using { /Verse.org/Random }
using { /Fortnite.com/Devices }

GenerateValue() : float =
    GetRandomFloat(0.0, 1.0)

# 名前がぶつかったときは、(モジュール名:)で明示する
using { CombatModule }
using { MagicModule }

ProcessDamage() : void =
    PhysicalDamage := (CombatModule:)CalculateDamage(100.0)
    MagicalDamage  := (MagicModule:)CalculateDamage(100.0)
🗂️
パスはグローバルな住所

/YourGame/Player/Inventoryのような形式で、世界中のどのモジュールも一意に指し示せます。/Verse.org/Verseは言語のコア機能、/Fortnite.com/DevicesはFortnite連携機能のように、公式モジュールにも同じ命名ルールが使われています。

17ふつう

永続化可能な型 ── セーブデータの金庫

プレイヤーの進行状況を「ゲームを終了しても消えない」ように保存するための仕組みがPersistable Typesです。

たとえ話でわかる 永続化

銀行の貸金庫を思い浮かべてください。あなたが帰宅しても(ゲームを終了しても)、貸金庫の中身(セーブデータ)は次に来店したとき(次にログインしたとき)もそのまま残っています。 ただし貸金庫には「持ち込めるものの決まりごと」があるように、永続化できるデータにも厳格なルールがあります。

verse
# <persistable>な構造体を定義する
player_stats := struct<persistable>:
    Level : int = 1
    Experience : int = 0
    GamesPlayed : int = 0

# プレイヤーごとにデータを紐づける weak_map として保存する
PlayerData : weak_map(player, player_stats) = map{}

GetOrCreateStats(Player : player) : player_stats =
    if (Existing := PlayerData[Player]):
        Existing
    else:
        NewStats := player_stats{}
        if (set PlayerData[Player] = NewStats) {}
        NewStats
永続化できるもの永続化できないもの
int / float / logic / string / charany / comparable / type
array / map / option / tuple(中身も永続化可能なら)rational / 関数型
<persistable>かつ<final>な構造体・クラス継承ありのクラス / インターフェース型
🏦
スキーマは「あとから変えにくい」

公開後にセーブデータの形を大きく変更するのは、実際の銀行の金庫のルールを後から変えるのと同じくらい大変です。設計段階で項目をよく吟味し、シンプルな値にはstructを優先しましょう(classより制約が少なく軽量です)。

18実践

実践: ミニゲームの状態管理パターン

上級編で学んだ知識を総動員して、「制限時間内に的をタップするミニゲーム」のコントローラーを設計してみましょう。 enumで状態を表現し、raceでタイムアウトを実現し、deferで後片付けをし、 Live VariablesでUI表示を自動同期させます。

verse — mini_game.verse
# ゲームの状態は今後増える可能性を考えて open にしておく
game_state := enum<open>:
    Ready
    Playing
    Cleared
    TimeUp

mini_game := class:
    var State : game_state = game_state.Ready
    var Score : int = 0

    # UIの表示用テキストは Score を自動で追いかける(Live Variables)
    var live ScoreText : string = "スコア: {Score}"

    RunRound(TimeLimitSeconds : float)<suspends> : void =
        set State = game_state.Playing
        defer:
            Print("ラウンド終了処理を実行しました")   # 必ず後片付けされる

        # 「的をタップし切る」処理と「制限時間」を競わせる
        race:
            block:
                PlayUntilCleared()
                set State = game_state.Cleared
            block:
                Sleep(TimeLimitSeconds)
                set State = game_state.TimeUp

        case (State):
            game_state.Cleared => Print("クリア! {ScoreText}")
            game_state.TimeUp  => Print("時間切れ…")
            _                    => Print("予期しない状態です")

    PlayUntilCleared()<suspends> : void =
        loop:
            Sleep(0.1)              # 中断ポイント(協調的キャンセルに対応)
            set Score += 10
            if (Score >= 100):
                break
🎮
この例に詰まっている考え方

raceによる「クリアかタイムアウトか」の競争、deferによる確実な後片付け、<suspends>の伝播、Live Variablesによる自動UI更新、enum<open>とcase式による将来を見据えた状態管理──ここまで学んできたすべての要素が、実際の1つの機能の中で自然に組み合わさっています。
