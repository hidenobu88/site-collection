01上級のキモ

エフェクトという「成分表示ラベル」

Verseの関数には、名前・引数・戻り値の他に、もうひとつ大事な情報が書かれています。それがエフェクト(効果)です。 「この関数は、実行中に何をする可能性があるか」を、< >で囲んで宣言します。

たとえ話でわかる エフェクト

スーパーで売っているお菓子の袋の裏にある「成分表示ラベル」を思い浮かべてください。 「小麦・卵・乳成分を含みます」と書かれていれば、アレルギーがある人はひと目で避けられますよね。

Verseのエフェクトも同じ役目です。<reads>と書かれていれば「この関数はゲームの状態を読み取ります」、 <writes>なら「状態を書き換えます」と、関数の中身を1行も読まなくても、何をする関数かパッケージの外側からわかるのです。 そしてコンパイラが、この表示が嘘になっていないかを厳密にチェックしてくれます。

verse
CalculateDamage(Base : float, Mult : float)<computes> : float =
    Base * Mult                    # 何も読み書きしない、純粋な計算

GetStatus(P : player)<reads> : string =
    if (P.Health > 50.0): "元気" else "負傷中"   # 状態を読むだけ

HealPlayer(P : player, Amount : float)<transacts> : void =
    set P.Health = Min(P.Health + Amount, 100.0)  # 状態を書き換える

エフェクトには大きく3つの「家族」があります。この地図を頭に入れておくと、これから先の章がすべてつながって見えてきます。

📦

Heapファミリー

computes / reads / writes / transacts ── メモリの読み書きに関する成分表示。

🎲

Cardinalityファミリー

decides ── 「失敗するかもしれない」という成分表示。

⏳

Suspensionファミリー

suspends ── 「時間をまたいで一時停止するかもしれない」という成分表示。

📝 演習問題

プレイヤーPの名前(P.Name)を読み取って挨拶文を作るだけの関数GreetPlayerに、 正しいエフェクト(<reads>)を付けてみましょう。

verse
GreetPlayer(P : player)<reads> : string =
    "ようこそ、{P.Name}さん!"
02上級のキモ

computes 〜 transacts の階層

Heapファミリーの4つは、権限の強さの階段になっています。

たとえ話でわかる 権限の階段

図書館の利用証を思い浮かべてください。「館内閲覧のみ」証では本を読むだけ。「貸出可」証があれば本を持ち帰って書き込みもできる──というように、 できることの範囲が段階的に広がっていきますよね。

エフェクトたとえできること
<computes>電卓を使うだけ純粋な計算のみ。何も読み書きしない
<reads>館内閲覧のみの利用証状態の読み取りが許可される
<writes>書き込み許可の利用証状態の変更が許可される
<transacts>(既定)フル権限の利用証読み取り・書き込み・確保すべて許可

重要なのは、この階段が「制限が少ない関数は、制限が多い場所でも代わりに使える」というサブタイピングの関係にあることです。 「純粋な計算しかしない関数」は、「読み取りをしてもよい」という場所に渡しても何の問題もありませんよね。

verse
PureAdd(X : int)<computes> : int = X + 1

# 「computes以上の権限を持つ関数ならOK」という場所にも、
# 一番権限の弱い computes 関数を渡せる
F : type{_(:int)<computes><decides> : int} = PureAdd   # 有効
🚫
ルール: 同じ指定子を2つ書けない

<computes><computes>のような重複はエラーになります。また<suspends>と<decides>は組み合わせられません。「一時停止するかもしれない」と「失敗するかもしれない」は、Verseでは意図的に別の枠組みとして扱われているためです。

📝 演習問題

次の3つの関数それぞれに、いちばんふさわしいエフェクト(computes/reads/writes)を考えて付けてみましょう。 ①2つのfloatを掛け算するだけの関数 ②プレイヤーのHPを読み取るだけの関数 ③プレイヤーのスコアに10点加算する関数。

verse
Multiply(A : float, B : float)<computes> : float = A * B

GetHealth(P : player)<reads> : float = P.Health

AddScore(P : player)<writes> : void =
    set P.Score += 10
03ふつう

decides エフェクトと失敗の伝播

中級編で学んだ「失敗」の考え方は、<decides>というエフェクトとして関数の成分表示に現れます。 そしてこの成分表示は、まるでバケツリレーのように呼び出し元へ伝わっていきます。

verse
# AttemptPurchase は自分自身が「失敗するかもしれない」ので <decides> を宣言
AttemptPurchase(Cost : int)<transacts><decides> : void =
    set PlayerGold = PlayerGold - Cost   # 一旦、暫定的に引いてみる
    PlayerGold >= 0                       # マイナスならここで失敗

AttemptPurchaseを呼び出す側の関数もまた、この失敗の可能性を受け止める(<decides>を宣言するか、 ifで失敗コンテキストに包む)必要があります。成分表示が正直に連鎖していくことで、 「どこかで失敗が握りつぶされて、気づかないバグになる」事故を未然に防いでいます。

⚠️
「失敗」と「実行時エラー」は別物

Err("メッセージ")で発生させる実行時エラーは、鍵が回らなかっただけの「失敗」とは違い、回復不可能な致命的な異常を表します。コールスタックを伝って処理が強制終了するため、「本当に続行不可能なとき」だけに使うべき、最後の手段です。

📝 演習問題

<transacts><decides>を持つ関数AttemptEnterを作り、年齢(Age)が18以上のときだけ成功して"入場OK"を返すようにしてみましょう。

verse
AttemptEnter(Age : int)<transacts><decides> : string =
    Age >= 18   # 18未満ならここで失敗
    "入場OK"
04上級のキモ

suspends と非同期処理の基本

普通の関数は「一瞬(1フレーム)で処理が終わる」ことが前提です。しかし「3秒待つ」「アニメーションが終わるまで待つ」といった、 時間をまたぐ処理をしたい関数には、<suspends>という成分表示が必要です。

たとえ話でわかる suspends

電子レンジでお弁当を温めているところを思い浮かべてください。「温め始める」というボタンを押した瞬間に処理は終わりません。 チンと鳴るまでの間、その場に立ち止まって待つ必要があります。<suspends>が付いた関数は、 この「電子レンジの前で待っている時間」を表現できる関数、というわけです。

verse
PlaySequence()<suspends> : void =
    PlayAnimation(Dance)
    Sleep(2.0)                  # 2秒間、実行を一時停止する
    PlaySound(FanfareSound)
📡
suspendsも伝播する

<decides>と同じように、<suspends>な関数を呼び出す関数自身も<suspends>を宣言する必要があります。「電子レンジの前で待つ人を呼びに行った人も、結局は一緒に待つことになる」というわけです。

📝 演習問題

「3秒カウントダウンしてから"スタート!"と表示する」Countdown関数を、<suspends>とSleepを使って書いてみましょう。

verse
Countdown()<suspends> : void =
    Print("3")
    Sleep(1.0)
    Print("2")
    Sleep(1.0)
    Print("1")
    Sleep(1.0)
    Print("スタート!")
05上級のキモ

並行処理 ① sync ── 全員そろうまで待つ

Verseの並行処理は「構造化並行処理」という設計で、並行タスクの寿命が、必ずコードの見た目のブロックに収まるようになっています。 4つの主な仲間、sync / race / rush / branchと、少し特殊なspawnを順番に見ていきましょう。まずはsyncです。

たとえ話でわかる sync

運動会の「大縄跳びリレー」を思い浮かべてください。すべてのチームが縄跳びを跳び終えるまで、次の種目には進めません。 全員がそろうまで、全体が待つ──これがsyncです。

verse
Results := sync:
    LoadTexture()
    LoadSound()
    LoadModel()

# 3つすべてのロードが完了してから、ここに到達する
ProcessData(Results(0), Results(1), Results(2))
🎮
向いている場面

ゲーム開始時に「テクスチャ・サウンド・モデル」など、複数の準備を同時並行で進め、すべてが終わってから次に進みたいときに最適です。1つずつ順番に待つより、ずっと速く準備が終わります。

📝 演習問題

OpenDoor()、PlaySound()、TurnOnLight()という3つの処理をsyncで並行実行し、 すべて終わったら「準備完了!」と表示するコードを書いてみましょう。

verse
sync:
    OpenDoor()
    PlaySound()
    TurnOnLight()

Print("準備完了!")
06上級のキモ

並行処理 ② race ── 早い者勝ち

たとえ話でわかる race

文字通り「徒競走」です。3人が同時にヨーイドンでスタートし、1着になった選手が決まった瞬間、まだ走っている他の選手たちはそこで棄権させられます。 raceは、最初に完了した処理の結果だけを受け取り、残りは自動的にキャンセルされます。

verse
Winner := race:
    SlowOperation()
    FastOperation()
    MediumOperation()

# FastOperationの結果を受け取り、他の2つは自動キャンセルされている
⏱️
タイムアウト処理の定番パターン

raceは「本来やりたい処理」と「制限時間のSleep」を競わせることで、タイムアウト機能を簡単に実装できます。制限時間の方が先にゴールしたら、本来の処理は自動的に打ち切られます。

📝 演習問題

「なぞなぞに正解する処理(WaitForAnswer())」と「5秒のタイムアウト」をraceで競わせ、 先にゴールした方に応じてメッセージを出し分けるコードを書いてみましょう。

verse
race:
    block:
        WaitForAnswer()
        Print("正解しました!")
    block:
        Sleep(5.0)
        Print("時間切れです")
07やや難しい

並行処理 ③ rush ── 一番乗りを見ながら、他も走らせ続ける

たとえ話でわかる rush

宿題と部活の朝練を同時に進める学生を想像してください。「とりあえず宿題が終わった時点で一旦チェックを受けるけれど、 朝練のランニングメニューはそのまま続けさせる」──rushは、最初の完了は教えてくれつつも、 raceと違って残りのタスクをキャンセルせず、裏側で走らせ続けます。

verse
FirstResult := rush:
    LongBackgroundTask()   # 時間がかかるが、最後までやり切ってほしい
    QuickCheck()            # すぐ終わる確認作業

# QuickCheckの結果を先に受け取れるが、LongBackgroundTaskは裏で継続中
💡
向いている場面

「素早い応答性がほしいけれど、時間のかかる処理も最後までちゃんと終わらせたい」という場面。ただしループの本体で直接使うことはできない、という制約があります。

📝 演習問題

「時間のかかるセーブ処理(SaveGameData())」と「すぐ終わるUI更新(UpdateSaveIcon())」を rushで組み合わせ、UI更新の結果を先に受け取りつつ、セーブ処理も裏側で最後まで完了させるコードを書いてみましょう。

verse
FirstDone := rush:
    SaveGameData()      # 時間がかかるが最後までやり切る
    UpdateSaveIcon()    # すぐ終わるので先に結果が返る
08やや難しい

並行処理 ④ branch と spawn ── バックグラウンド任務

たとえ話でわかる branch と spawn

branchは「打ち上げ花火」です。導火線に火をつけたら、その場で結果を見届けずに次の作業に進みます。 花火は勝手に打ち上がりますが、その場面(スコープ)が終わったら、花火自体も自動的に片付けられます。
spawnは「独立した長期プロジェクト」です。担当者(呼び出し元の処理)がすでに退社していても、 プロジェクト自体はスコープをまたいで生き続けます。

verse
# branch: 花火を打ち上げて、その場はすぐ先に進む
branch:
    PlayBackgroundEffect()
    UpdateSystemAsync()
# ここにはすぐ到達する(バックグラウンドはまだ実行中)

# spawn: スコープを超えて独立して生き続けるタスクを作る
BackgroundTask : task(int) = spawn{ LongRunningWork() }

# task型が持つ操作
BackgroundTask.Cancel()          # キャンセルを依頼する
Result : int = BackgroundTask.Await()   # 完了を待って結果を受け取る
キーワードたとえいつ使う
sync大縄跳びリレー(全員待つ)複数の初期化処理をまとめて待ちたいとき
race徒競走(1着以外は失格)タイムアウトなど、最速の結果だけ欲しいとき
rush宿題と朝練を並行(両方やり切る)速い応答と完全な処理、両方ほしいとき
branch打ち上げ花火(発射して次へ)結果を待たずに背景処理をしたいとき
spawn独立した長期プロジェクトスコープをまたいで生き続く常駐処理
✏️ ミニクイズ
Q. 「制限時間3秒以内に敵を倒せなければタイムアウト」を実装したい。どのキーワードが最適?
正解はB。「敵を倒す処理」と「3秒のSleep」をraceで競わせれば、先にゴールした方の結果だけが採用される、典型的なタイムアウトパターンになります。
📝 演習問題

branchを使って、「花火の演出(PlayFireworks())」を打ち上げつつ、 その場ですぐに「Print("次の処理に進みます")」を実行するコードを書いてみましょう。

verse
branch:
    PlayFireworks()

Print("次の処理に進みます")
09やや難しい

協調的キャンセル ── 律儀な職人のように

raceで負けたタスクや、Cancel()を呼ばれたタスクは、実はその瞬間に即座には止まりません。

たとえ話でわかる 協調的キャンセル

職人さんに「もう作業をやめてください」と伝えても、ノコギリを動かしている途中でいきなり手を止めたりはしませんよね。 「キリのいいところ(次の作業の切れ目)まで来たら、やめます」と応じるのが自然です。 Verseのキャンセルもこれと同じ「協調的」な仕組みです。タスクは、あらかじめ決められた「中断ポイント」 (Sleepや関数呼び出しなど)に来たときだけ、「あ、キャンセルされてる」と気づいて止まります。

verse
ResponsiveLoop()<suspends> : void =
    for (I := 0..10000):
        ExpensiveOperation(I)
        Sleep(0.0)          # 中断ポイント。ここでキャンセル信号をチェックする
🪚
中断ポイントがないと、止まれない

もし重い処理の中にSleepや関数呼び出しなどの中断ポイントが一切なければ、キャンセルを頼んでもすぐには反応してくれません。時間のかかるループには、こまめに中断ポイントを挟むのが良い設計です。また、親タスクがキャンセルされると、その子タスクにもキャンセルが自動的に伝わっていきます。

📝 演習問題

0〜4999まで数えるCountUpという<suspends>関数を書き、各回でSleep(0.0)という中断ポイントを挟んで、 途中でキャンセルされたときにすぐ反応できるようにしてみましょう。

verse
CountUp()<suspends> : void =
    for (I := 0..4999):
        Print("{I}")
        Sleep(0.0)   # 中断ポイント。キャンセルされたらここで止まれる
10ふつう

defer とリソース管理

「使ったら必ず片付ける」処理を、忘れずに実行してくれるのがdeferです。

たとえ話でわかる defer

学校の「教室の電気を消す当番」のようなものです。用事が急に入って教室を飛び出すことになっても(キャンセルや早期リターンが起きても)、 deferで予約しておいた「電気を消す」という後片付けは、教室を出るタイミングで必ず実行されます。

verse
ProcessWithTimeout()<suspends> : void =
    race:
        block:
            Resource := AcquireResource()
            defer:
                ReleaseResource(Resource)   # 途中でキャンセルされても必ず実行
            LongTask(Resource)
        block:
            Sleep(10.0)                     # 10秒経ったらタイムアウト
📝 演習問題

「ドアを開く(OpenDoor())」→「中で作業する(DoWork())」という処理の後に、 deferを使って必ずドアを閉じる(CloseDoor())ようにしてみましょう。

verse
DoRoomWork()<suspends> : void =
    OpenDoor()
    defer:
        CloseDoor()   # 途中で何が起きても、必ずドアを閉じる
    DoWork()
11上級のキモ

トランザクションとロールバック

<transacts>エフェクトを持つ関数の中で行った変更は、もし途中で失敗したら、まるで最初から何も起きなかったかのように取り消されます。

たとえ話でわかる トランザクション

ゲームで強敵に挑む前に、必ずセーブしてから挑みますよね。もし負けてしまったら、ロードしてやり直せば、挑戦前の状態にきれいに巻き戻ります。 <transacts>の中身は、この「セーブ→挑戦→失敗したら自動ロード」を、Verseが裏側で自動的にやってくれる仕組みです。

verse
AttemptPurchase(Cost : int)<transacts><decides> : void =
    set PlayerGold = PlayerGold - Cost   # 暫定的に所持金を減らす(仮の変更)
    PlayerGold >= 0                       # マイナスになったら…

# ↑ もし失敗したら、PlayerGoldは「減らす前」の状態に自動で巻き戻る。
#   「所持金だけ減って、商品は手に入らない」という中途半端な事故が起きない。
🛡️
なぜこれが重要なのか

他の多くの言語では「途中まで処理が進んだ状態で例外が起きて、データが中途半端に壊れる」というバグがよく起きます。Verseはこの問題を、言語の仕組みそのもので根本から解決しています。これは「投機的実行(Speculative Execution)」とも呼ばれます。

📝 演習問題

AttemptPurchaseを参考に、プレイヤーのHPを10消費してスキルを発動するAttemptSkill (<transacts><decides>)を書いてみましょう。HPが0未満になる場合は失敗し、自動的に巻き戻るようにします。

verse
AttemptSkill()<transacts><decides> : void =
    set PlayerHP -= 10   # 暫定的にHPを減らす
    PlayerHP >= 0          # マイナスになったら失敗、自動で巻き戻る
12上級のキモ

Live Variables ── 自動で計算し直される変数

普通の変数は、一度計算したら値は固定です。しかしLive Variablesを使うと、 「元になる値が変わったら、自動的に再計算される変数」を作れます。

たとえ話でわかる Live Variables

表計算ソフト(エクセル)のセルを思い浮かべてください。B1セルに「=A1+1」という数式を入れておくと、 A1の値を変えるたびに、B1は手で計算し直さなくても自動で更新されますよね。 Live Variablesは、まさにこの「数式が入ったセル」をプログラムの変数として使えるようにしたものです。

verse
var X : int = 0
var Y : int = 0

set live X = Y + 1   # X は Y を「数式」として追いかけるようになる
set Y = 5
Print(X)               # → 6 (Yが変わると、Xも自動で追従する)

宣言の仕方にはいくつかバリエーションがあります。

verse
var live X : int = Exp     # 可変なリアクティブ変数として宣言
live Y : int = Exp          # 不変なリアクティブ変数として宣言
set live X = Exp            # 既存の変数にリアクティブ性を後付け

ゲームでよくある「上限・下限のあるHPバー」も、Live Variablesで自然に表現できます。

verse
clamp := class:
    var Lower : int = 0
    var Upper : int = 100
    Evaluate(Value : int)<reads> : int =
        if (Value < Upper) then
            if (Value > Lower) then Value else Lower
        else Upper

# Health に値を入れると、自動的に0〜100の範囲に丸められる
var BaseHealth->Health : clamp.Evaluate = 50
set Health = 120     # BaseHealthは120になるが、Health自体は100で頭打ち
📏
依存関係は実行時に決まる

「数式(条件式)がどの変数に依存しているか」は、コンパイル時ではなく実行時に動的に決まります。if (Z > 0) then X else Yという数式なら、Zの値によって「Xを見張る」か「Yを見張る」かが切り替わります。またこの数式に<writes>エフェクトを持たせることはできません──あくまで「見張って再計算するだけ」の存在だからです。

await / upon / when / batch

Live Variablesと組み合わせて使う、時間・条件に関する4つの便利な仲間を紹介します。

⏰

await

目覚まし時計のように、条件が満たされるまでその場で待ち続け、満たされたら1回だけ先に進みます。

🚨

upon

ホームセキュリティのセンサーのように、条件が最初にtrueになった瞬間、1回だけコードを実行します。

📹

when

常時監視カメラのように、条件がtrueである間、変化のたびに何度でもコードを実行し続けます。

🧾

batch

スーパーのレジのように、複数の変更をまとめてから、最後に1回だけ会計(通知)します。

verse
# await: Xが変化するまで待って、1回だけ先に進む
await{X <> OldX}
Print("Xが変わった: {X}")

# upon: HPが0以下になった瞬間、1回だけ死亡フラグを立てる
upon(Health <= 0):
    set IsDead = true

# when: スコアが変わるたびに、表示用の値を更新し続ける
when(Score):
    set DisplayedScore = Score

# batch: XとYをまとめて更新し、途中経過では反応させない
batch:
    set X = 2
    set Y = 10
# ここでようやく、リアクティブな反応がまとめて1回発生する

uponを使って、Coins(所持金)が1000以上になった瞬間だけ「大金持ちの称号を獲得!」と1回だけ表示するコードを書いてみましょう。

Refinement Types ── 値の範囲を絞る鋳型

型に「この範囲の値しか許さない」という追加ルールを持たせられるのがRefinement Types(改良型)です。

たとえ話でわかる Refinement Types

金属加工の「鋳型(いがた)」を思い浮かべてください。溶けた金属を流し込んでも、鋳型の形からはみ出た部分は作れません。 Refinement Typesは、まさに「この範囲の値しか通さない鋳型」を型として定義できる機能です。

verse
# 0.0以上1.0以下の値しか受け付けない「鋳型」
percent := type{_X : float where 0.0 <= _X, _X <= 1.0}

Opacity : percent = 0.5     # OK -- 鋳型の範囲内
# BadOpacity : percent = 1.5  # コンパイルは通っても実行時に失敗する
📐
制約に書けるのは「リテラル」だけ

鋳型のルールに書けるのは0.0や1.0のような、その場に直接書かれた値(リテラル)だけです。変数や関数呼び出しを条件に混ぜることはできません。

メタタイプ ── 「型そのもの」を値として扱う

Verseでは型そのものを値として持ち運べます(type型)。これをさらに便利に使うための3つの道具があります。

たとえ話でわかる メタタイプ

図鑑の「動物」のページを思い浮かべてください。subtype(animal)は「動物図鑑に載っているすべての種類(犬・猫・鳥…)」を指す言葉です。 しかし「動物」という抽象的な概念そのものは、実際に1匹連れてくることはできません。
一方concrete_subtype(animal)は、「実際にペットショップで購入できる、具体的な種類」だけに絞り込んだリストです。

verse
# subtype(T): Tの仲間である「型」を値として表す
AnimalType : subtype(animal) = dog

# concrete_subtype(T): 実際にインスタンス化できる具体的な型
EntityType : concrete_subtype(entity) = player
NewEntity := EntityType{}          # 実際に「作れる」

# castable_subtype(T): <castable>マーク付きの型限定
ComponentType : castable_subtype(component) = physics_component
🧬
何がうれしいのか

「実行時に、どの敵キャラを生成するかを動的に切り替えたい」といったケースで活躍します。コンパイル時の型安全性を保ったまま、実行時のポリモーフィズム(多態性)を実現できるのがメタタイプの強みです。

📝 演習問題

verse
enemy := class:
    var HP : int = 100

    var HP : int = 30

永続化可能な型 ── セーブデータの金庫

プレイヤーの進行状況を「ゲームを終了しても消えない」ように保存するための仕組みがPersistable Typesです。

たとえ話でわかる 永続化

銀行の貸金庫を思い浮かべてください。あなたが帰宅しても(ゲームを終了しても)、貸金庫の中身(セーブデータ)は次に来店したとき(次にログインしたとき)もそのまま残っています。 ただし貸金庫には「持ち込めるものの決まりごと」があるように、永続化できるデータにも厳格なルールがあります。

verse
# <persistable>な構造体を定義する
player_stats := struct<persistable>:
    Level : int = 1
    Experience : int = 0
    GamesPlayed : int = 0

# プレイヤーごとにデータを紐づける weak_map として保存する
PlayerData : weak_map(player, player_stats) = map{}

GetOrCreateStats(Player : player) : player_stats =
    if (Existing := PlayerData[Player]):
        Existing
    else:
        NewStats := player_stats{}
        if (set PlayerData[Player] = NewStats) {}
        NewStats

int / float / logic / string / charany / comparable / type
array / map / option / tuple(中身も永続化可能なら)rational / 関数型
<persistable>かつ<final>な構造体・クラス継承ありのクラス / インターフェース型
🏦

実践: ミニゲームの状態管理パターン

上級編で学んだ知識を総動員して、「制限時間内に的をタップするミニゲーム」のコントローラーを設計してみましょう。 enumで状態を表現し、raceでタイムアウトを実現し、deferで後片付けをし、 Live VariablesでUI表示を自動同期させます。

verse — mini_game.verse
# ゲームの状態は今後増える可能性を考えて open にしておく
game_state := enum<open>:
    Ready
    Playing
    Cleared
    TimeUp

mini_game := class:
    var State : game_state = game_state.Ready
    var Score : int = 0

    # UIの表示用テキストは Score を自動で追いかける(Live Variables)
    var live ScoreText : string = "スコア: {Score}"

    RunRound(TimeLimitSeconds : float)<suspends> : void =
        set State = game_state.Playing
        defer:
            Print("ラウンド終了処理を実行しました")   # 必ず後片付けされる

        # 「的をタップし切る」処理と「制限時間」を競わせる
        race:
            block:
                PlayUntilCleared()
                set State = game_state.Cleared
            block:
                Sleep(TimeLimitSeconds)
                set State = game_state.TimeUp

        case (State):
            game_state.Cleared => Print("クリア! {ScoreText}")
            game_state.TimeUp  => Print("時間切れ…")
            _                    => Print("予期しない状態です")

    PlayUntilCleared()<suspends> : void =
        loop:
            Sleep(0.1)              # 中断ポイント(協調的キャンセルに対応)
            set Score += 10
            if (Score >= 100):
                break
🎮
この例に詰まっている考え方

raceによる「クリアかタイムアウトか」の競争、deferによる確実な後片付け、<suspends>の伝播、Live Variablesによる自動UI更新、enum<open>とcase式による将来を見据えた状態管理──ここまで学んできたすべての要素が、実際の1つの機能の中で自然に組み合わさっています。

シーングラフ応用 ── なめらかなアニメーション制御

中級編ではMoveToEaseで2点間を往復させました。ここでは本格的なScene Graphの仕組みを使い、 「現在地を記録して呼び戻す」テクニックと、「複数の経由地点を一気に登録して自動再生する」テクニックの2つを身につけます。

たとえ話でわかる キーフレームアニメーション

パラパラ漫画(紙芝居)を思い出してください。1枚1枚の絵を「キーフレーム」として順番に並べておけば、 めくるスピードを調整するだけで、複雑な動きも滑らかに再生できますよね。

Verseのkeyframed_movement_componentは、まさにこの「紙芝居めくり係」です。 「どこに(Transform)」「どれくらいの時間で(Duration)」「どんな速度変化で(Easing)」動くかを1枚ずつのカードにして まとめて登録(SetKeyframes)すれば、あとはPlay()の合図ひとつで、続けて自動再生してくれます。

📍まず基本: 現在地を記録して呼び戻す

いちばんシンプルな応用は、「今の位置を記録しておき、あとで正確にそこへ戻す」パターンです。チェックポイントやリセット機能でよく使われます。

verse
using { /Fortnite.com/Creative }
using { /Verse.org/Simulation }

checkpoint_prop_device := class(creative_device):
    @editable
    Door : creative_prop = creative_prop{}

    var SavedTransform : transform = transform{}

    OnBegin<override>()<suspends> : void =
        # 今の姿勢(位置・回転)をまるごと記録しておく
        set SavedTransform = Door.GetGlobalTransform()

    ResetDoor() : void =
        # 記録しておいた姿勢に、ワンコマンドで正確に戻す
        Door.SetGlobalTransform(SavedTransform)

🎞️応用: 複数の経由地点を自動再生する

巡回する敵の足場や、複数の停留所を回るエレベーターは、キーフレームをまとめて登録するとシンプルに書けます。

verse — patrol_platform_device.verse
using { /Fortnite.com/Creative }
using { /Verse.org/SceneGraph/KeyframedMovement }
using { /Verse.org/Simulation }

patrol_platform_device := class(creative_device):
    # UEFNの詳細パネルで、プロップに追加した「Keyframed Movement」コンポーネントを割り当てる
    @editable
    Movement : keyframed_movement_component = keyframed_movement_component{}

    OnBegin<override>()<suspends> : void =
        Keyframes : []keyframed_movement_delta = array{
            keyframed_movement_delta{                                     # 停留所1
                Transform := transform{Translation := vector3{X := 0.0, Y := 0.0, Z := 0.0}},
                Duration := 2.0, Easing := move_to_ease_type.EaseInOut
            },
            keyframed_movement_delta{                                     # 停留所2
                Transform := transform{Translation := vector3{X := 500.0, Y := 0.0, Z := 300.0}},
                Duration := 2.5, Easing := move_to_ease_type.EaseInOut
            },
            keyframed_movement_delta{                                     # 停留所3
                Transform := transform{Translation := vector3{X := 500.0, Y := 500.0, Z := 300.0}},
                Duration := 2.5, Easing := move_to_ease_type.EaseInOut
            }
        }
        Movement.SetKeyframes(Keyframes)
        Movement.Play()   # 停留所1→2→3の順に、自動でなめらかに巡回する
🛠️
この分野はアップデートが速い

Scene Graph関連のAPIはUEFNの中でも比較的新しく、細かいプロパティ名やコンポーネントの取得方法がバージョンごとに調整されることがあります。骨組みの考え方(キーフレーム配列を作ってSetKeyframes→Play)は変わりませんが、実際にUEFNで書くときはVerseエディタのオートコンプリート(Ctrl+Space)で最新の候補を確認する習慣をつけましょう。

UEFNには、自分のアイランドの中でV-Bucksと引き換えにアイテムを販売できる「In-Island Transactions(島内取引)」 という仕組みがあります。2025年12月から、開発者は自分のアイランドから直接アイテムを販売できるようになりました。

島内取引 応用編 ── 購入を検知してごほうびを渡す

商品棚を作っただけでは、まだお店は完成しません。「本当に支払いが完了したか」を確実に確認してから、 ごほうびを手渡す必要があります。

たとえ話でわかる 誠実なレジ係

模擬店の店員さんを思い浮かべてください。「お客さんが払ったって言ってたから、たぶん大丈夫だろう」と商品を渡すのは危険です。 誠実な店員さんは、レジの記録(領収書)を見て、本当に支払いが記録されたことを確認してから商品を渡しますよね。

Verseでも同じで、BuyOfferを呼んだ「その場の結果」だけを信用するのではなく、 GetEntitlementChangedEventという「レジの記録係」からの通知を確認してから、ごほうびを渡すのが正しい作法です。

verse — reward_shop_device.verse
using { /Fortnite.com/IslandTransactions }
using { /Fortnite.com/Devices }
using { /Verse.org/Simulation }

reward_shop_device := class(creative_device):
    @editable
    ShopButton : button_device = button_device{}
    @editable
    BonusGranter : item_granter_device = item_granter_device{}

    OnBegin<override>()<suspends> : void =
        ShopButton.InteractedWithEvent.Subscribe(OnShopButtonPressed)
        # レジの記録係(購入完了通知)を、最初にひとつだけ登録しておく
        GetEntitlementChangedEvent().Subscribe(OnEntitlementChanged)

    OnShopButtonPressed(Agent : agent) : void =
        ShowOffersDialog(Agent, array{golden_pickaxe_offer{}})

    # 「本当に買えたとき」だけ、ここが呼ばれる
    OnEntitlementChanged(Agent : agent, Entitlement : subtype(entitlement)) : void =
        if (Entitlement = golden_pickaxe_entitlement):
            BonusGranter.GrantItem(Agent)   # 領収書を確認してから、初めてごほうびを渡す
            Print("購入ありがとうございます! ボーナスアイテムを渡しました")
🔍
所持確認にはGetPurchasedEntitlementsを使う

「このプレイヤーはすでにこの商品を持っているか?」を確認したいときはGetPurchasedEntitlements(Agent)を使います。すでに持っている耐久アイテムを二重に売ってしまう事故を防げます。

⚡
この設計、どこかで見た形では?

「実行結果を直接信じず、確定した通知(イベント)を待ってから重要な処理を行う」という考え方は、11章のトランザクションとロールバックで学んだ「セーブ→挑戦→失敗したら自動ロード」の安全設計と同じ精神です。お金が関わる島内取引では、この慎重さがとくに重要になります。

22集大成

集大成: 全アセット統合ミニゲーム

最後の実践では、これまで学んだボタン・トリガー・アイテム付与・テレポート・Scene Graph・島内取引のすべてを1つの ミニゲームにまとめます。「制限時間内に動く足場を渡りきり、ゴールで報酬を受け取り、お店でボーナスアイテムも買える」という、 実際のUEFNアイランドでそのままテストできる規模の完成形です。

verse — grand_finale_device.verse
using { /Fortnite.com/Devices }
using { /Fortnite.com/Characters }
using { /Fortnite.com/Creative }
using { /Fortnite.com/IslandTransactions }
using { /Verse.org/Simulation }

course_state := enum<open>:
    Ready
    Running
    Cleared
    TimeUp

grand_finale_device := class(creative_device):
    @editable StartButton   : button_device      = button_device{}   # ①スタート合図
    @editable FinishTrigger : trigger_device      = trigger_device{}  # ②ゴール判定
    @editable MovingPlatform: creative_prop        = creative_prop{}  # ③動く足場(Scene Graph)
    @editable RewardGranter : item_granter_device = item_granter_device{}  # ④クリア報酬
    @editable ShopButton    : button_device       = button_device{}   # ⑤ボーナスショップ

    var live State : course_state = course_state.Ready
    var live StatusText : string = "スタートボタンを押してください"

    OnBegin<override>()<suspends> : void =
        StartButton.InteractedWithEvent.Subscribe(OnStart)
        FinishTrigger.TriggeredEvent.Subscribe(OnFinish)
        ShopButton.InteractedWithEvent.Subscribe(OnShop)
        GetEntitlementChangedEvent().Subscribe(OnEntitlementChanged)

    OnStart(Agent : agent) : void =
        RunCourse(Agent)

    RunCourse(Agent : agent)<suspends> : void =
        set State = course_state.Running
        set live StatusText = "足場を渡ってゴールを目指せ!"
        defer:
            Print("コースの後片付けをしました")   # 10章: defer

        # ③足場をなめらかに往復させながら(スコープを抜けたら自動キャンセル)
        branch:
            MovingPlatform.MoveToEase(
                vector3{X := 500.0, Y := 0.0, Z := 300.0}, IdentityRotation(),
                vector3{X := 1.0, Y := 1.0, Z := 1.0}, 3.0,
                move_to_ease_type.EaseInOut, animation_mode.PingPong)

        # ゴールか、60秒のタイムアウトかを競わせる(6章: race)
        race:
            block:
                # ②OnFinishがStateをClearedに書き換えるまで、ここで待つ(13章: await)
                await{State = course_state.Cleared}
            block:
                Sleep(60.0)
                if (State = course_state.Running):
                    set State = course_state.TimeUp

        case (State):
            course_state.Cleared =>
                set live StatusText = "クリア! ごほうびを渡します"
                RewardGranter.GrantItem(Agent)                 # ④報酬付与
                if (FortChar := Agent.GetFortCharacter[]):     # ゴール後に開始地点へ戻す
                    if (FortChar.TeleportTo[vector3{X := 0.0, Y := 0.0, Z := 100.0}, IdentityRotation()]) {}
            course_state.TimeUp =>
                set live StatusText = "時間切れ…もう一度挑戦しよう"
            _ =>
                set live StatusText = "予期しない結果です"

    # ②トリガーを踏んだ瞬間、レース中の待機(await)を解いてクリア扱いにする
    OnFinish(MaybeAgent : ?agent) : void =
        if (State = course_state.Running):
            set State = course_state.Cleared

    # ⑤ショップとentitlement購入検知(21章の応用そのまま)
    OnShop(Agent : agent) : void =
        ShowOffersDialog(Agent, array{golden_pickaxe_offer{}})

    OnEntitlementChanged(Agent : agent, Entitlement : subtype(entitlement)) : void =
        if (Entitlement = golden_pickaxe_entitlement):
            Print("ボーナスアイテムを購入いただきありがとうございます!")

📝 最終チャレンジ問題

①trigger_deviceを踏むと、②<transacts><decides>な関数でスタミナを20消費し(0未満なら失敗)、 ③成功したらcreative_propをMoveToEaseでなめらかに1回だけ移動させるという、ダッシュギミック dash_pad_deviceを、この章までの知識だけで作ってみましょう。

ヒント: trigger_deviceのSubscribe(01章相当)、transacts&decides(03章・11章)、MoveToEase(19章)を1つにまとめます。
verse — dash_pad_device.verse
dash_pad_device := class(creative_device):
    @editable
    Pad : trigger_device = trigger_device{}
    @editable
    Platform : creative_prop = creative_prop{}

    var Stamina : int = 100

    OnBegin<override>()<suspends> : void =
        Pad.TriggeredEvent.Subscribe(OnPadTriggered)

    OnPadTriggered(MaybeAgent : ?agent) : void =
        DoDash()

    # ②スタミナ消費に失敗したら、何も動かさずに静かに終わる
    ConsumeStamina()<transacts><decides> : void =
        set Stamina -= 20
        Stamina >= 0   # マイナスになったら失敗、自動で巻き戻る

    DoDash()<suspends> : void =
        if (ConsumeStamina[]):
            # ③スタミナが足りていたときだけ、なめらかにダッシュ演出
            Platform.MoveToEase(
                vector3{X := 300.0, Y := 0.0, Z := 0.0}, IdentityRotation(),
                vector3{X := 1.0, Y := 1.0, Z := 1.0}, 0.5,
                move_to_ease_type.EaseOut, animation_mode.OneShot)
        else:
            Print("スタミナが足りません")
