MODULE 01

ジェネリクスと型安全な設計

コレクションやリポジトリ層で必ず使うジェネリクス。「なんとなく <T> を書く」から「意図を持って設計する」レベルに引き上げます。

1-1. ジェネリッククラスとメソッド

ジェネリクスは「型をあとから決められるようにする仕組み」です。Objectで何でも受け取る設計と違い、コンパイル時に型が保証されるため、実行時のClassCastExceptionを防げます。クラスだけでなく、メソッド単体にも型パラメータを持たせられます。

Box.java
public class Box<T> {
    private T content;

    public void set(T content) {
        this.content = content;
    }

    public T get() {
        return content;
    }
}

// メソッド単体のジェネリクス（クラスとは独立して型パラメータを持てる）
public class Pair {
    public static <A, B> boolean sameClass(A a, B b) {
        return a.getClass().equals(b.getClass());
    }
}
💡
実務Tipsリポジトリ層の共通処理（findByIdやsaveなど）をinterface Repository<T, ID>のような形で抽象化しておくと、エンティティが増えても実装をコピペせずに済みます。Spring Data JPAのJpaRepository<T, ID>もこの考え方です。
EX 1-1-a

ジェネリックなスタックを実装する

基礎確認

任意の型を格納できるスタックSimpleStack<T>を実装してください。push(T item)、pop()（空ならIllegalStateExceptionを投げる）、peek()、isEmpty()を持たせます。内部の保持にはjava.util.ArrayListを使ってかまいません。

ヒント: フィールドはprivate final List<T> items = new ArrayList<>();のように宣言します。
解答例を見る
SimpleStack.java
public class SimpleStack<T> {
    private final List<T> items = new ArrayList<>();

    public void push(T item) {
        items.add(item);
    }

    public T pop() {
        if (isEmpty()) {
            throw new IllegalStateException("stack is empty");
        }
        return items.remove(items.size() - 1);
    }

    public T peek() {
        if (isEmpty()) {
            throw new IllegalStateException("stack is empty");
        }
        return items.get(items.size() - 1);
    }

    public boolean isEmpty() {
        return items.isEmpty();
    }
}

ArrayListの末尾操作はO(1)なので、末尾をスタックの先頭とみなすのが定石です。先頭(index 0)を使うと要素移動が発生し、パフォーマンスが落ちます。

EX 1-1-b

2つの値を安全に入れ替えるユーティリティ

基礎確認

配列の2要素を入れ替える汎用メソッドstatic <T> void swap(T[] array, int i, int j)をユーティリティクラスArrayUtilsに実装してください。型は問いません（Integer[]でもString[]でも動くこと）。

解答例を見る
ArrayUtils.java
public final class ArrayUtils {
    private ArrayUtils() {}

    public static <T> void swap(T[] array, int i, int j) {
        T tmp = array[i];
        array[i] = array[j];
        array[j] = tmp;
    }
}

ユーティリティクラスはインスタンス化する意味がないため、privateコンストラクタで生成を禁止するのが定石です。

1-2. 境界ワイルドカードと型消去

List<Integer>はList<Number>のサブタイプではありません。これがジェネリクスの「非変」という性質です。この制約を緩めるのが境界ワイルドカードで、PECS原則（Producer Extends, Consumer Super）で使い分けます。

Wildcards.java
// Producer（値を「取り出す」側）は extends
public static double sumOf(List<? extends Number> numbers) {
    double sum = 0;
    for (Number n : numbers) {
        sum += n.doubleValue();
    }
    return sum;
}

// Consumer（値を「入れる」側）は super
public static void fillWithZero(List<? super Integer> list, int count) {
    for (int i = 0; i < count; i++) {
        list.add(0);
    }
}

また、ジェネリクスの型情報はコンパイル時にのみ存在し、実行時にはすべて消去されます（型消去）。そのためnew T()やinstanceof List<String>のような記述はできません。実行時に型を扱いたい場合はClass<T>を引数として渡す設計が定番です。

⚠️
やりがちなミスList<Object>とList<?>を混同しがちですが、前者は「Objectしか入れられない」、後者は「何が入っているか分からないので基本的に読み取り専用として扱う」という全く違う意味です。
EX 1-2-a

PECS原則でコピーメソッドを書く

応用

srcからdestへ全要素をコピーするstatic <T> void copyAll(List<? extends T> src, List<? super T> dest)を実装してください。copyAll(List<Integer> の値, List<Number> の入れ物)のような呼び出しが型エラーなくコンパイルできることを確認してください。

ヒント: srcからは読み取るだけ、destへは書き込むだけ、という役割を意識するとPECSがそのまま当てはまります。
解答例を見る
CopyUtils.java
public static <T> void copyAll(List<? extends T> src, List<? super T> dest) {
    for (T item : src) {
        dest.add(item);
    }
}

// 呼び出し例
List<Integer> ints = List.of(1, 2, 3);
List<Number> numbers = new ArrayList<>();
copyAll(ints, numbers); // OK: IntegerはNumberのサブタイプ
EX 1-2-b

型消去の影響を説明する

応用

次のコードはコンパイルエラーになります。理由をコメントで説明したうえで、Class<T>を引数で受け取る方式に書き換えて、正しく動くcreateInstanceメソッドを完成させてください。

public static <T> T createInstance() {
    return new T(); // コンパイルエラー
}
解答例を見る

理由: ジェネリクスの型パラメータTは実行時には消去されており、JVMは「Tが具体的に何のクラスか」を知る手段がないため、new T()を実体化できません。

Factory.java
public static <T> T createInstance(Class<T> type) throws Exception {
    return type.getDeclaredConstructor().newInstance();
}

// 呼び出し例
User user = createInstance(User.class);
✅ モジュール1完了の目安: PECS原則を人に説明できて、なぜnew T()が書けないか理解できていればOKです。
MODULE 02

Stream APIとコレクション操作の実務パターン

for文をStreamに置き換えるだけでなく、「実務で読みやすいStreamの書き方」と「やってはいけない使い方」を押さえます。

2-1. Streamの生成とmap/filter/reduce

Streamは「コレクションに対する処理のパイプライン」です。filterで絞り込み、mapで変換し、collectやreduceで集約する、という3段階で考えると設計しやすくなります。中間操作（filter, mapなど）は遅延評価され、終端操作（collect, forEachなど）が呼ばれて初めて実行されます。

StreamBasics.java
List<Employee> employees = ...;

// 30歳以上の社員の名前一覧を取得
List<String> names = employees.stream()
        .filter(e -> e.getAge() >= 30)
        .map(Employee::getName)
        .toList(); // Java 16+

// 給与の合計
int totalSalary = employees.stream()
        .mapToInt(Employee::getSalary)
        .sum();

// reduceで最も給与が高い社員を求める
Optional<Employee> topEarner = employees.stream()
        .reduce((a, b) -> a.getSalary() >= b.getSalary() ? a : b);
⚠️
やりがちなミスStreamは一度しか消費できません。同じStreamに対して2回collectするとIllegalStateExceptionになります。使い回したい場合は、都度list.stream()のようにコレクションから作り直してください。
EX 2-1-a

注文リストから合計金額を求める

基礎確認

次のOrderレコードのリストに対し、statusが"PAID"のものだけを対象に、price * quantityの合計金額を求めるコードをStreamで書いてください。

record Order(String status, int price, int quantity) {}

List<Order> orders = List.of(
    new Order("PAID", 1200, 2),
    new Order("CANCELLED", 500, 1),
    new Order("PAID", 800, 3)
);
解答例を見る 
int total = orders.stream()
        .filter(o -> o.status().equals("PAID"))
        .mapToInt(o -> o.price() * o.quantity())
        .sum();
// 1200*2 + 800*3 = 4800
EX 2-1-b

単語の出現数トップ3を求める

応用

List<String> wordsから、それぞれの単語の「文字数」の合計を求める代わりに、文字数が5文字以上の単語だけを大文字化してリストにするコードをStreamで実装してください。重複は除去し、アルファベット順に並べてください。

解答例を見る 
List<String> result = words.stream()
        .filter(w -> w.length() >= 5)
        .map(String::toUpperCase)
        .distinct()
        .sorted()

distinct()とsorted()はどちらも中間操作ですが、内部的に全要素をバッファする必要があるため、巨大なStreamでは順序とコストに注意しましょう。

2-2. Collectors応用とOptionalの正しい使い方

実務のStreamで一番よく使うのがCollectors.groupingByとCollectors.toMapです。集計処理をfor文で書くよりも、意図が読みやすくなります。

CollectorsDemo.java
// 部署ごとに社員をグルーピング
Map<String, List<Employee>> byDept = employees.stream()
        .collect(Collectors.groupingBy(Employee::getDepartment));

// 部署ごとの平均給与
Map<String, Double> avgSalaryByDept = employees.stream()
        .collect(Collectors.groupingBy(
                Employee::getDepartment,
                Collectors.averagingInt(Employee::getSalary)));

// idをキーにしたMapを作る（キー重複時は例外になる点に注意）
Map<Long, Employee> byId = employees.stream()
        .collect(Collectors.toMap(Employee::getId, e -> e));

Optionalは「値がないかもしれない」ことを型で表現する仕組みです。フィールドやメソッド引数には使わないのが原則で、あくまで「戻り値」として使います。

OptionalDemo.java
public Optional<Employee> findById(long id) {
    return employees.stream()
            .filter(e -> e.getId() == id)
            .findFirst();
}

// 悪い例: get()をいきなり呼ぶとNoSuchElementExceptionの危険
Employee e = findById(99).get();

// 良い例: orElseThrowで意図を明示する
Employee e2 = findById(99)
        .orElseThrow(() -> new NoSuchElementException("employee not found: 99"));

// 値があれば使う、なければ何もしない
findById(1).ifPresent(emp -> System.out.println(emp.getName()));
💡
実務TipsOptional.isPresent()のあとにget()を呼ぶ書き方はほぼ不要です。map・orElse・orElseGet・orElseThrowを組み合わせれば、if文なしで安全に値を扱えます。

EX 2-2-b

Optionalチェーンでニックネームを取得する

応用

findById(long)がOptional<Employee>を返すとして、EmployeeにはOptional<String> getNickname()があります。id指定で社員を検索し、ニックネームがあればそれを、なければgetName()を、社員自体が見つからなければ"unknown"を返す1行の式を、if文を使わずに書いてください。

ヒント: Optional#flatMapを使うと、Optionalの中のOptionalを平坦化できます。

String label = findById(id)

EX 2-2-c

不変なOptionalフィールドを持つDTOのリファクタリング

発展

次のクラスには実務でよくあるアンチパターンがあります。問題点を指摘し、Optionalをフィールドに使わない設計に書き換えてください。

public class UserProfile {
    private Optional<String> middleName; // フィールドにOptional

    public UserProfile(Optional<String> middleName) {
        this.middleName = middleName;
    }
}
解答例を見る

問題点: OptionalはSerializableを実装しておらず、フィールドに使うとシリアライズできません。また呼び出し側がnullを渡すとその時点でNPEになり、Optionalの「安全に空を表現する」メリットが失われます。

public class UserProfile {
    private final String middleName; // nullを許容するフィールドとして扱う

    public UserProfile(String middleName) {
        this.middleName = middleName; // nullでもOK
    }

    // 取得時にOptionalへ変換して公開する
    public Optional<String> getMiddleName() {
        return Optional.ofNullable(middleName);
    }
}

「フィールドや引数は素の型（nullを許容）、メソッドの戻り値だけOptionalで包む」というのが実務での定石です。

✅ モジュール2完了の目安: groupingByで集計できて、Optionalをフィールドに使わない理由を説明できればOKです。
MODULE 03

オブジェクト指向設計とデザインパターン

パターン名を覚えることが目的ではなく、「if/switchの分岐が増え続けるコード」をどう設計し直すか、という視点で学びます。

3-1. SOLID原則とStrategy・Factory Method

SOLIDのうち実務で特に効いてくるのは単一責任の原則（SRP）と開放閉鎖の原則（OCP）です。「割引ロジックを条件分岐で足していく」ようなコードは、Strategyパターンで書き換えると新しい割引を追加してもif文を触らずに済みます。

DiscountStrategy.java
public interface DiscountStrategy {
    int apply(int price);
}

public class NoDiscount implements DiscountStrategy {
    public int apply(int price) { return price; }
}

public class PercentDiscount implements DiscountStrategy {
    private final int percent;
    public PercentDiscount(int percent) { this.percent = percent; }
    public int apply(int price) { return price * (100 - percent) / 100; }
}

public class Order {
    private final DiscountStrategy discount;
    public Order(DiscountStrategy discount) { this.discount = discount; }
    public int finalPrice(int price) { return discount.apply(price); }
}

Factory Methodは「どの実装クラスを生成するか」の判断をカプセル化するパターンです。呼び出し側は具象クラスを意識せずインターフェースだけを扱えます。

NotifierFactory.java
public interface Notifier {
    void send(String message);
}

public class NotifierFactory {
    public static Notifier create(String channel) {
        return switch (channel) {
            case "email" -> new EmailNotifier();
            case "sms" -> new SmsNotifier();
            default -> throw new IllegalArgumentException("unknown channel: " + channel);
        };
    }
}
EX 3-1-a

料金計算をStrategyパターンに書き換える

応用

次のif文だらけのcalcShippingFeeを、Strategyパターンを使って書き換えてください。地域は"STANDARD", "REMOTE", "OVERSEAS"の3種類です。

public int calcShippingFee(String region, int weight) {
    if (region.equals("STANDARD")) {
        return 500 + weight * 10;
    } else if (region.equals("REMOTE")) {
        return 1500 + weight * 15;
    } else if (region.equals("OVERSEAS")) {
        return 3000 + weight * 30;
    }
    throw new IllegalArgumentException("unknown region");
}
解答例を見る 
public interface ShippingFeeStrategy {
    int calc(int weight);
}

public class StandardShipping implements ShippingFeeStrategy {
    public int calc(int weight) { return 500 + weight * 10; }
}
public class RemoteShipping implements ShippingFeeStrategy {
    public int calc(int weight) { return 1500 + weight * 15; }
}
public class OverseasShipping implements ShippingFeeStrategy {
    public int calc(int weight) { return 3000 + weight * 30; }
}

public class ShippingFeeStrategyFactory {
    public static ShippingFeeStrategy of(String region) {
        return switch (region) {
            case "STANDARD" -> new StandardShipping();
            case "REMOTE" -> new RemoteShipping();
            case "OVERSEAS" -> new OverseasShipping();
            default -> throw new IllegalArgumentException("unknown region");
        };
    }
}

// 呼び出し側
int fee = ShippingFeeStrategyFactory.of(region).calc(weight);

新しい地域が増えても、既存クラスを変更せずに新しいShippingFeeStrategy実装を追加するだけで済みます。これがOCP（開放閉鎖の原則）です。

EX 3-1-b

単一責任の原則違反を見つける

基礎確認

次のUserServiceクラスはSRP（単一責任の原則）に違反しています。何が問題か指摘し、責任ごとにクラスを分割した設計を提案してください（コードは短くて構いません）。

public class UserService {
    public void register(String email, String password) {
        // 1. バリデーション
        if (!email.contains("@")) throw new IllegalArgumentException("invalid email");
        // 2. パスワードのハッシュ化
        String hashed = hash(password);
        // 3. DB保存
        jdbcTemplate.update("INSERT INTO users ...", email, hashed);
        // 4. メール送信
        mailClient.send(email, "登録ありがとうございます");
    }
}
解答例を見る

問題点: バリデーション・パスワードのハッシュ化・永続化・通知という4つの異なる責任が1メソッドに詰め込まれています。仕様変更（例: メール文面の変更）のたびにUserService全体を触ることになり、テストも書きにくくなります。

public class UserService {
    private final UserValidator validator;
    private final PasswordHasher hasher;
    private final UserRepository repository;
    private final WelcomeMailSender mailSender;

    public void register(String email, String password) {
        validator.validate(email, password);
        String hashed = hasher.hash(password);
        User user = repository.save(new User(email, hashed));
        mailSender.send(user);
    }
}

UserServiceは「登録という流れの調整役」に徹し、個々の責任は専用クラスに委譲します。

3-2. Builder・Observer・スレッドセーフなSingleton

コンストラクタの引数が4つ5つと増えてきたら、Builderパターンの出番です。JavaではLombokの@Builderが有名ですが、まずは素の実装を理解しておきましょう。

User.java
public class User {
    private final String name;
    private final int age;
    private final String email;

    private User(Builder b) {
        this.name = b.name;
        this.age = b.age;
        this.email = b.email;
    }

    public static class Builder {
        private String name;
        private int age;
        private String email;

        public Builder name(String name) { this.name = name; return this; }
        public Builder age(int age) { this.age = age; return this; }
        public Builder email(String email) { this.email = email; return this; }

        public User build() { return new User(this); }
    }
}

// 呼び出し例
User user = new User.Builder()
        .name("山田太郎")
        .age(28)
        .email("yamada@example.com")
        .build();

Observerパターンは「状態変化を複数の相手に通知する」仕組みで、GUIのイベントリスナーやPub/Subの基礎になります。

StockTicker.java
public interface PriceListener {
    void onPriceChanged(int newPrice);
}

public class StockTicker {
    private final List<PriceListener> listeners = new ArrayList<>();
    private int price;

    public void subscribe(PriceListener listener) {
        listeners.add(listener);
    }

    public void updatePrice(int newPrice) {
        this.price = newPrice;
        for (PriceListener l : listeners) {
            l.onPriceChanged(newPrice);
        }
    }
}

Singletonは「インスタンスを1つに保証したい」ときに使いますが、マルチスレッド環境では初期化のタイミングでバグを生みやすいパターンでもあります。enumを使った実装が最もシンプルで安全です。

AppConfig.java
public enum AppConfig {
    INSTANCE;

    private final Map<String, String> settings = new ConcurrentHashMap<>();

    public String get(String key) {
        return settings.get(key);
    }
}

// 呼び出し例
AppConfig.INSTANCE.get("timeout");
⚠️
やりがちなミスif (instance == null) instance = new AppConfig();という素朴なSingletonは、複数スレッドが同時にこの行を実行するとインスタンスが2つ作られる可能性があります。enum、またはsynchronizedを使った遅延初期化（double-checked locking）が必要です。
EX 3-2-a

HTTPリクエスト設定オブジェクトをBuilderで実装する

応用

url（必須）、method（省略時は"GET"）、timeoutMs（省略時は3000）、headers（Map<String,String>、省略時は空）を持つHttpRequestConfigをBuilderパターンで実装してください。urlが設定されないままbuild()された場合はIllegalStateExceptionを投げてください。

解答例を見る 
public class HttpRequestConfig {
    private final String url;
    private final String method;
    private final int timeoutMs;
    private final Map<String, String> headers;

    private HttpRequestConfig(Builder b) {
        this.url = b.url;
        this.method = b.method;
        this.timeoutMs = b.timeoutMs;
        this.headers = b.headers;
    }

    public static class Builder {
        private String url;
        private String method = "GET";
        private int timeoutMs = 3000;
        private final Map<String, String> headers = new HashMap<>();

MODULE 04

例外設計とエラーハンドリングの実務

「とりあえずtry-catchで囲む」から卒業し、意図が伝わる例外設計を身につけます。

4-1. 独自例外クラスの設計

JavaにはCheck例外（Exception直系）とUnchecked例外（RuntimeException系）があります。実務では「呼び出し側が回復できる可能性がある」ものだけをChecked例外にし、それ以外はUnchecked例外にする、という判断基準が広く使われています。

Exceptions.java
// 回復可能: 呼び出し側が「在庫を待つ」「別商品を選ぶ」など対処できる
public class OutOfStockException extends Exception {
    public OutOfStockException(String productId) {
        super("out of stock: " + productId);
    }
}

// 回復不能に近い: プログラミングミスやデータ不整合
public class InvalidOrderStateException extends RuntimeException {
    public InvalidOrderStateException(String message) {
        super(message);
    }
}

例外には「原因（cause）」を必ず連結しましょう。e.getMessage()だけでは、元々どこで何が起きたのか追跡できなくなります。

try {
    paymentClient.charge(orderId, amount);
} catch (PaymentClientException e) {
    // causeを渡さないと、元のスタックトレースが失われる
    throw new PaymentFailedException("payment failed for order " + orderId, e);
}
💡
実務Tips例外メッセージには「何のIDで」「何をしようとして」失敗したかを必ず含めましょう。ログ検索やバグ調査のスピードが大きく変わります。

public class InsufficientBalanceException extends Exception {

残高不足は「チャージすれば再試行できる」回復可能なケースなので、呼び出し元にキャッチを強制できるChecked例外が適しています。

4-2. try-with-resourcesと例外の握りつぶし防止

AutoCloseableを実装したリソース（Connection, FileInputStreamなど）は、必ずtry-with-resourcesで扱いましょう。finallyで手動closeするより簡潔で、closeの呼び忘れも防げます。

TryWithResources.java
// 複数リソースもセミコロン区切りで書ける。宣言と逆順にcloseされる
try (var in = new FileInputStream("input.txt");
     var out = new FileOutputStream("output.txt")) {
    in.transferTo(out);
} catch (IOException e) {
    throw new UncheckedIOException(e);
}

もう一つの実務での鉄則は「catchブロックを空にしない」ことです。何もしないcatch (Exception e) {}は、障害の原因を見えなくする最悪のパターンです。

// アンチパターン: エラーがなかったことになる
try {
    riskyOperation();
} catch (Exception e) {
    // 何もしない
}

// 最低限、ログには残す
try {
    riskyOperation();
} catch (Exception e) {
    log.warn("riskyOperation failed, falling back to default", e);
}

応用

public class Stopwatch implements AutoCloseable {
    private final String label;

MODULE 05

並行処理の基礎と実務

Threadを直接newする機会は実務では少なく、ExecutorServiceやCompletableFutureを使うのが標準です。まずは仕組みの理解から。

5-1. Thread・ExecutorServiceの基本

スレッドを都度new Thread()で作ると、生成コストが高く、数の制御もできません。ExecutorServiceでスレッドプールを使い回すのが実務での基本です。

ExecutorDemo.java
ExecutorService executor = Executors.newFixedThreadPool(4);

List<Future<Integer>> futures = new ArrayList<>();
for (int i = 0; i < 10; i++) {
    int taskId = i;
    futures.add(executor.submit(() -> heavyCalculation(taskId)));
}

int total = 0;
for (Future<Integer> f : futures) {
    total += f.get(); // 結果が出るまでブロックする
}

executor.shutdown(); // 使い終わったら必ずshutdownする
⚠️
やりがちなミスexecutor.shutdown()を呼び忘れると、非デーモンスレッドが残り続けてアプリケーションが終了しなくなります。try-with-resources対応のExecutorService（Java 19+のAutoCloseable実装）や、finallyでのshutdownを徹底しましょう。
EX 5-1-a

複数URLのステータスを並行取得する（擬似コード）

応用

List<String> urlsそれぞれに対してint checkStatus(String url)（時間のかかるダミー処理と考えてよい）を並行実行し、全結果をList<Integer>として集める処理を、固定4スレッドのExecutorServiceを使って実装してください。

解答例を見る 
ExecutorService executor = Executors.newFixedThreadPool(4);
try {
    List<Future<Integer>> futures = urls.stream()
            .map(url -> executor.submit(() -> checkStatus(url)))
            .toList();

    List<Integer> results = new ArrayList<>();
    for (Future<Integer> f : futures) {
        results.add(f.get());
    }
    return results;
} finally {
    executor.shutdown();
}

スレッドプールのサイズ選定を説明する

基礎確認

「CPUバウンドな処理（計算中心）」と「I/Oバウンドな処理（DBアクセスや外部API呼び出し）」とで、適切なスレッドプールサイズの考え方がなぜ異なるのか、2〜3行で説明してください。

解答例を見る

CPUバウンドな処理はCPUコア数を超えてスレッドを増やしても、コンテキストスイッチのオーバーヘッドが増えるだけで性能は上がりにくいため、コア数前後に抑えます。一方I/Oバウンドな処理はスレッドが「待っている」時間が長く、その間CPUは空いているため、コア数より多いスレッド数（例: コア数の数倍）にすることでスループットを上げられます。

5-2. CompletableFutureとスレッドセーフな設計

CompletableFutureは、非同期処理を「チェーン」で組み立てられる仕組みです。複数の非同期処理を組み合わせたいとき、Future#get()で毎回ブロックするより読みやすく効率的なコードになります。

CompletableFutureDemo.java
// ユーザー情報と注文履歴を並行取得し、両方そろってから合成する
CompletableFuture<User> userFuture =
        CompletableFuture.supplyAsync(() -> userClient.fetch(userId));
CompletableFuture<List<Order>> ordersFuture =
        CompletableFuture.supplyAsync(() -> orderClient.fetchAll(userId));

CompletableFuture<UserPage> pageFuture = userFuture.thenCombine(
        ordersFuture,
        (user, orders) -> new UserPage(user, orders));

UserPage page = pageFuture.join(); // 結果を待つ（例外はCompletionExceptionに包まれる）

複数スレッドから共有される可変状態は、synchronizedか、java.util.concurrentのスレッドセーフなコレクション（ConcurrentHashMapなど）で保護します。volatileは「他スレッドからの可視性」だけを保証し、複合操作（読み取り→計算→書き込み）の原子性は保証しない点に注意しましょう。

// NG: volatileだけではインクリメントの原子性が保証されない
private volatile int counter = 0;
public void increment() { counter++; } // 実は read-modify-write の複合操作

// OK: AtomicIntegerを使う
private final AtomicInteger counter = new AtomicInteger();
public void increment() { counter.incrementAndGet(); }

EX 5-2-b

複数スレッドから安全にカウントするクラスを実装する

発展

複数スレッドからrecord(String key)が呼ばれ、キーごとの呼び出し回数を数えるAccessCounterクラスを、スレッドセーフに実装してください。get(String key)で現在のカウントを取得できるようにします。

ヒント: ConcurrentHashMap<String, AtomicInteger>とcomputeIfAbsentの組み合わせが定番です。
解答例を見る 
public class AccessCounter {
    private final ConcurrentHashMap<String, AtomicInteger> counts = new ConcurrentHashMap<>();

    public void record(String key) {
        counts.computeIfAbsent(key, k -> new AtomicInteger()).incrementAndGet();
    }

    public int get(String key) {
        AtomicInteger count = counts.get(key);
        return count == null ? 0 : count.get();
    }
}

computeIfAbsentは「キーがなければ生成して登録」を1つの原子的な操作として行えるため、自前でnullチェック+putするより安全です。

public Map<String, Long> countLevels(Path logFile) throws IOException {

6-2. JUnit5とテスト設計の基本

テストは「AAAパターン（Arrange - Act - Assert）」で書くと読みやすくなります。準備・実行・検証をコメントやメソッド分割で明確に分けましょう。

DiscountCalculatorTest.java
class DiscountCalculatorTest {

    @Test
    void tenPercentDiscount_appliesCorrectly() {
        // Arrange
        DiscountCalculator calculator = new DiscountCalculator();

        // Act
        int result = calculator.applyPercent(1000, 10);

        // Assert
        assertEquals(900, result);
    }

    @ParameterizedTest
    @CsvSource({
        "1000, 0, 1000",
        "1000, 50, 500",
        "1000, 100, 0"
    })
    void variousPercentages(int price, int percent, int expected) {
        DiscountCalculator calculator = new DiscountCalculator();
        assertEquals(expected, calculator.applyPercent(price, percent));
    }

    @Test
    void negativePercent_throwsException() {
        DiscountCalculator calculator = new DiscountCalculator();
        assertThrows(IllegalArgumentException.class,
                () -> calculator.applyPercent(1000, -10));
    }
}

外部のDB・API呼び出しなど「差し替えたい依存」はインターフェースにしておくと、テスト時にモック（偽物の実装やMockitoのようなモックライブラリ）に差し替えられます。

// インターフェースに依存しているので、テスト時はモック実装を注入できる
public class OrderService {
    private final PaymentGateway paymentGateway;

    public OrderService(PaymentGateway paymentGateway) {
        this.paymentGateway = paymentGateway;

    public void checkout(Order order) {
        paymentGateway.charge(order.total());

}

// テストコードでは本物のPaymentGatewayの代わりに、
// 常にtrueを返すだけのテスト用実装や、Mockitoの mock(PaymentGateway.class) を注入する
