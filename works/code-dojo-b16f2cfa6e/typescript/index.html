MODULE 01

型システムの基礎を固める

Union・Intersection・Literal Typesは、以降のすべてのモジュールの土台になります。「anyで逃げない」書き方をここで固めます。

1-1. Union・Intersection・Literal Types

Union型（A | B）は「AまたはB」、Intersection型（A & B）は「AかつB（両方の性質を持つ）」を表します。Literal Typesは、値そのものを型として扱う仕組みで、"pending" | "paid" | "cancelled"のような「取りうる値を限定した型」を作れます。

types-basics.ts
type OrderStatus = "pending" | "paid" | "cancelled";

function label(status: OrderStatus): string {
  switch (status) {
    case "pending": return "処理待ち";
    case "paid": return "支払い済み";
    case "cancelled": return "キャンセル";
  }
}

// Intersection: 2つの型の性質をすべて持つ
type Timestamped = { createdAt: Date };
type Named = { name: string };
type NamedEvent = Timestamped & Named;

const event: NamedEvent = { name: "リリース会", createdAt: new Date() };
💡
実務Tipsstringで状態を表すより、Literal Typesの合併型にしておくと、タイプミス（"pendign"など）をコンパイル時に検出できます。API通信のstatusフィールドなどに積極的に使いましょう。
🤔
なぜこうなるのか現実のデータには「AかBのどちらか」（例: 支払い済みかキャンセルか）や、「AとBの両方の性質を持つ」（例: 一般ユーザーの情報も管理者権限も両方持つ）という形が非常によく登場します。これを普通のstringや1つのオブジェクト型だけで表現しようとすると、「本当はこの値しか来ないはず」という前提がコード上のどこにも書かれず、実行時になって初めて想定外の値に気づくことになります。UnionとIntersectionは、こうした「現実の形」をそのままコンパイラに教えるための道具です。
🥤
たとえ話自動販売機のボタンを思い浮かべてください。ボタンに書かれている飲み物は「コーラ・お茶・水」のどれかだけです(Union型)。もし「好きな飲み物名を紙に書いてください」という方式だったら、"コーラ"のつもりで"コーラー"と書き間違えても、機械はその間違いに気づけません。ボタン方式(Literal Typesの合併)なら、そもそも存在しない飲み物は選べないので、間違えようがないのです。Intersectionは「メガネをかけたサッカー選手」のように、2つの特徴を両方持つ人を1人で表すイメージです。
EX 1-1-a

信号の色をLiteral Typesで表現する

基礎確認

"red" | "yellow" | "green"のUnion型TrafficLightを定義し、その値を受け取って「止まれ」「注意」「進め」を返すdescribe(light: TrafficLight): stringを実装してください。

解答例を見る 
type TrafficLight = "red" | "yellow" | "green";

function describe(light: TrafficLight): string {
  switch (light) {
    case "red": return "止まれ";
    case "yellow": return "注意";
    case "green": return "進め";
  }
}
EX 1-1-b

Intersection型でロール付きユーザーを表現する

応用

BaseUser（id: number, name: string）とAdminPermissions（canDeleteUser: boolean, canEditBilling: boolean）を定義し、両方の性質を持つAdminUser型をIntersectionで作成してください。そのうえで、AdminUser型の値を1つ作成してください。

解答例を見る 
type BaseUser = { id: number; name: string };
type AdminPermissions = { canDeleteUser: boolean; canEditBilling: boolean };
type AdminUser = BaseUser & AdminPermissions;

const admin: AdminUser = {
  id: 1,
  name: "管理者A",
  canDeleteUser: true,
  canEditBilling: false,
};

1-2. 型ガードとNarrowing

Union型の値を扱うとき、TypeScriptはtypeofやin、instanceofなどのチェックを通じて型を絞り込みます（Narrowing）。さらに複雑な条件は「ユーザー定義型ガード（is構文）」として関数に切り出せます。

type-guards.ts
type ApiResult =
  | { kind: "success"; data: string[] }
  | { kind: "error"; message: string };

function handle(result: ApiResult) {
  if (result.kind === "success") {
    // ここでは result.data が使える（Narrowing済み）
    console.log(result.data.length);
  } else {
    console.log(result.message);
  }
}

// ユーザー定義型ガード
function isString(value: unknown): value is string {
  return typeof value === "string";
}

function printLength(value: unknown) {
  if (isString(value)) {
    console.log(value.length); // valueはstringとして扱える
  }
}
⚠️
やりがちなミスanyを使うとNarrowingの恩恵がすべて失われます。外部から来る未知のデータにはanyではなくunknownを使い、型ガードで絞り込んでから使いましょう。
🤔
なぜこうなるのかunknownは「何が来るか分からないので、確認するまでは何もさせない」型です。一方anyは「型チェックを丸ごとお休みする」型で、確認せずに何でも操作できてしまいます。typeofやin、ユーザー定義型ガードは、その「確認作業」そのものです。確認が済んだ範囲だけ、コンパイラはその型に応じた操作を許可してくれます。anyを使うと、この「確認してから使う」という安全装置ごと外してしまうことになります。
📦
たとえ話知らない人から届いた荷物(unknown)を想像してください。開けて中身を確認する前に食べたりしませんよね。「中身を確認してから、それが食べ物だと分かって初めて食べる」というのが型ガードの考え方です。anyは「確認しないで何でも口に入れていいよ」と言っているようなもので、実は危険な考え方なのです。
EX 1-2-a

unknownな値を安全に扱う

基礎確認

引数value: unknownを受け取り、数値なら2倍にして返し、文字列ならそのまま返し、それ以外ならnullを返すnormalize(value: unknown): number | string | nullを実装してください。

解答例を見る 
function normalize(value: unknown): number | string | null {
  if (typeof value === "number") {
    return value * 2;
  }
  if (typeof value === "string") {
    return value;
  }
  return null;
}
EX 1-2-b

ユーザー定義型ガードでシェイプを判定する

応用

次のShape型に対し、ユーザー定義型ガードisCircle(shape: Shape): shape is Circleを実装したうえで、それを使って面積を計算するarea(shape: Shape): numberを実装してください（円はπr²、四角形は幅×高さ。円周率はMath.PIを使用）。

type Circle = { type: "circle"; radius: number };
type Rectangle = { type: "rectangle"; width: number; height: number };
type Shape = Circle | Rectangle;
解答例を見る 
function isCircle(shape: Shape): shape is Circle {
  return shape.type === "circle";
}

function area(shape: Shape): number {
  if (isCircle(shape)) {
    return Math.PI * shape.radius ** 2;
  }
  return shape.width * shape.height;
}

実はこのケースではshape.typeを直接switchで見るだけでもNarrowingは効きますが、判定ロジックが複雑・再利用したい場合はユーザー定義型ガードに切り出すと見通しが良くなります。

✅ モジュール1完了の目安: unknownとanyの違いを説明でき、型ガードでNarrowingできればOKです。
MODULE 02

ジェネリクスと関数型のテクニック

「なんとなく<T>をつける」から「制約と推論を意図的に設計する」レベルへ。

2-1. ジェネリック関数と制約

ジェネリクスは呼び出し時に渡された値から型が自動推論されます。extendsで制約をかけると、「どんな型でも受け取れるが、最低限これらのプロパティは持っている」という設計ができます。

generics.ts
// 制約なし: どんな型でもそのまま返す
function identity<T>(value: T): T {
  return value;
}

// 制約あり: idプロパティを持つ型に限定する
function findById<T extends { id: number }>(items: T[], id: number): T | undefined {
  return items.find((item) => item.id === id);
}

const users = [{ id: 1, name: "太郎" }, { id: 2, name: "花子" }];
const found = findById(users, 1); // Tは自動的に { id: number; name: string } と推論される
💡
実務TipsAPIレスポンスの共通ラッパーtype ApiResponse<T> = { data: T; meta: { total: number } }のように、ジェネリクスを使うとエンドポイントごとに型定義をコピペせずに済みます。
🤔
なぜこうなるのか制約なしのジェネリクス<T>は「何でも受け取れるが、中身については何も分からないので何もできない箱」です。<T extends { id: number }>のように制約を付けると、「中身が何であれ、idというプロパティだけは必ず持っている」ということをコンパイラに保証させられます。これにより「自由に何でも受け取れる」柔軟さを保ちながら、必要な操作（idでの検索など）だけは安全に行えるようになります。
🪪
たとえ話「なんでも屋さん」に「IDカードだけは見せてね」とお願いする場面を想像してください。相手が犬でも猫でもロボットでも構いませんが、「IDカードを持っていること」だけは保証されています。だからIDカードを使った仕事（名前を探す、番号で照合するなど）は安心して頼めますよね。T extends { id: number }は、まさに「中身は自由だけど、このIDカードだけは絶対に持っている」という約束なのです。
EX 2-1-a

配列の先頭N件を返すジェネリック関数

基礎確認

任意の型の配列を受け取り、先頭n件を返すtake<T>(items: T[], n: number): T[]を実装してください。

解答例を見る 
function take<T>(items: T[], n: number): T[] {
  return items.slice(0, n);
}
EX 2-1-b

制約付きジェネリクスでキー指定の並び替えを実装する

応用

sortByKey<T, K extends keyof T>(items: T[], key: K): T[]を実装してください。keyで指定したプロパティの値（数値または文字列）で昇順に並び替えます。keyof Tを使うことで、存在しないプロパティ名を渡すとコンパイルエラーになるようにしてください。

解答例を見る 
function sortByKey<T, K extends keyof T>(items: T[], key: K): T[] {
  return [...items].sort((a, b) => {
    const av = a[key];
    const bv = b[key];
    if (av < bv) return -1;
    if (av > bv) return 1;
    return 0;
  });
}

// 呼び出し例
sortByKey(users, "name"); // OK
// sortByKey(users, "age"); // usersにageが無ければコンパイルエラー

[...items].sort(...)のようにスプレッドでコピーしてからソートすることで、元の配列を破壊しない（副作用のない）関数になります。

2-2. 高階関数とユーティリティ型の組み合わせ

関数を引数や戻り値として扱う「高階関数」は、TypeScriptでは関数の型もきちんと表現できます。組み込みのUtility Types（Partial, Pick, Omitなど）と組み合わせると、既存の型から柔軟に新しい型を作れます。

higher-order.ts
type User = { id: number; name: string; email: string; age: number };

// Partial: すべてのプロパティを省略可能にする（更新用DTOなどでよく使う）
function updateUser(id: number, patch: Partial<User>): void { /* ... */ }
updateUser(1, { name: "新しい名前" }); // 他のプロパティは省略できる

// Pick: 特定のプロパティだけを抜き出す
type UserSummary = Pick<User, "id" | "name">;

// Omit: 特定のプロパティを除いた型を作る
type UserWithoutEmail = Omit<User, "email">;

// 高階関数: 関数を返す関数
function withLogging<Args extends unknown[], R>(
  fn: (...args: Args) => R
): (...args: Args) => R {
  return (...args: Args) => {
    console.log("call with", args);
    return fn(...args);
  };
}

const add = (a: number, b: number) => a + b;
const loggedAdd = withLogging(add); // (a: number, b: number) => number として推論される
🤔
なぜこうなるのかPartialやOmitがなければ、更新用の型・作成用の型・一覧表示用の型を、元の型からそれぞれコピペで作ることになります。すると元の型にプロパティを1つ追加したとき、コピペした先すべてを手作業で直す必要が生まれ、直し忘れがバグの温床になります。Utility Typesは「元の型を単一の情報源(Single Source of Truth)として、そこから必要な形だけを自動的に導く」ための仕組みです。高階関数も同様に、元の関数を書き換えずに「ログ出力」のような共通処理を後から付け加えられます。
👕
たとえ話洋服の「サイズ違いバージョン」を毎回一から作るのは大変ですよね。それより「元のデザインから袖だけ短くする」(Omitで一部を取り除く)、「全部のボタンを外せるようにする」(Partialで全部省略可能にする)というように、元のデザイン(元の型)を土台にして一部だけ変えるほうが効率的です。高階関数は「同じ服に後からワッペンを縫い付ける」ようなもので、元の服自体は変えずに新しい機能を追加できます。
EX 2-2-a

PickとOmitでDTOを作る

基礎確認

次のProduct型から、「一覧表示用（id, name, priceだけ）」のProductListItemをPickで、「作成リクエスト用（idを除いたもの）」のCreateProductInputをOmitで、それぞれ作成してください。

type Product = {
  id: number;
  name: string;
  price: number;
  description: string;
  stock: number;
};
解答例を見る 
type ProductListItem = Pick<Product, "id" | "name" | "price">;
type CreateProductInput = Omit<Product, "id">;
EX 2-2-b

関数を1回だけ実行するonceを実装する

発展

渡した関数を「初回呼び出し時だけ実行し、以降は最初の戻り値をキャッシュして返す」once<Args extends unknown[], R>(fn: (...args: Args) => R): (...args: Args) => Rを実装してください。

ヒント: クロージャで「実行済みかどうか」と「キャッシュした戻り値」を保持します。
解答例を見る 
function once<Args extends unknown[], R>(
  fn: (...args: Args) => R
): (...args: Args) => R {
  let called = false;
  let cache: R;

  return (...args: Args): R => {
    if (!called) {
      cache = fn(...args);
      called = true;
    }
    return cache;
  };
}

// 呼び出し例
const initOnce = once(() => {
  console.log("初期化処理を実行");
  return { ready: true };
});
initOnce(); // "初期化処理を実行" と出力
initOnce(); // 何も出力されず、キャッシュされた値が返る
✅ モジュール2完了の目安: Partial/Pick/Omitを使い分けられて、高階関数の型を自分で書ければOKです。
MODULE 03

高度な型操作

組み込みのUtility Typesが「どう実装されているか」を知ると、自分で必要な型を組み立てられるようになります。

3-1. Mapped Typesと自作Utility Types

Mapped Typesは「既存の型のすべてのプロパティに対して、同じ変換を適用する」仕組みです。実はPartial<T>やReadonly<T>もMapped Typesで実装されています。

mapped-types.ts
// 標準ライブラリのPartialの実装（簡略版）
type MyPartial<T> = {
  [K in keyof T]?: T[K];
};

// 標準ライブラリのReadonlyの実装（簡略版）
type MyReadonly<T> = {
  readonly [K in keyof T]: T[K];
};

// 自作: すべてのプロパティをnull許容にする
type Nullable<T> = {
  [K in keyof T]: T[K] | null;
};

type User = { id: number; name: string };
type NullableUser = Nullable<User>;
// { id: number | null; name: string | null }
💡
実務Tipsフォームの入力値は「すべて未確定」な状態を扱うことが多いため、Partial<T>や自作のNullable<T>で「未入力を許容する型」を作っておくと、フォーム用の型とAPI送信用の型をきれいに分離できます。
🤔
なぜこうなるのか標準のPartialやReadonlyがどう実装されているかを知ると、「既存の型のすべてのプロパティに、同じ変換を機械的に適用する」という一般化されたテクニックそのものを学べます。これが分かれば、標準に無い変換(nullを許容する、readonlyを外すなど)も自分で組み立てられるようになります。車輪の再発明をするのではなく、「車輪の仕組みを理解して、自分の車に合わせて調整する」というのがMapped Typesを学ぶ意味です。
📋
たとえ話クラス全員の連絡帳に、同じハンコを1つずつ押していく作業を想像してください。keyof Tで「クラスの名簿(プロパティの一覧)」を取得し、名簿にある全員(すべてのキー)に同じ処理を適用します。Partialは「全員の連絡帳に『提出は任意です』というハンコを押す」、Readonlyは「全員の連絡帳に『書き換え禁止』のハンコを押す」ようなものです。
EX 3-1-a

Requiredを自作する

応用

標準のRequired<T>と同じ働きをするMyRequired<T>（すべてのプロパティを必須にするMapped Type）を実装してください。

ヒント: オプショナル修飾子?を打ち消すには-?を使います。
解答例を見る 
type MyRequired<T> = {
  [K in keyof T]-?: T[K];
};

type PartialUser = { id?: number; name?: string };
type FullUser = MyRequired<PartialUser>;
// { id: number; name: string }
EX 3-1-b

特定のキーだけ変更可能にするMutableを実装する

発展

全プロパティがreadonlyな型Tから、指定したキーKだけ書き込み可能に戻すMutable<T, K extends keyof T>を実装してください。

ヒント: Omitで対象外のプロパティを残しつつ、対象プロパティだけ-readonlyを付けたMapped Typeを交差型(&)で合成します。
解答例を見る 
type Mutable<T, K extends keyof T> = Omit<T, K> & {
  -readonly [P in K]: T[P];
};

type Config = {
  readonly host: string;
  readonly port: number;
  readonly debug: boolean;
};

type EditablePort = Mutable<Config, "port">;
// host, debugはreadonlyのまま、portだけ書き換え可能になる
EX 3-1-c

keyofと組み合わせてキー配列を検証する

応用

User型のキー名の配列だけを許可するpickFields<T, K extends keyof T>(obj: T, keys: K[]): Pick<T, K>を実装してください。存在しないキー名を渡すとコンパイルエラーになることを確認してください。

解答例を見る 
function pickFields<T, K extends keyof T>(obj: T, keys: K[]): Pick<T, K> {
  const result = {} as Pick<T, K>;
  for (const key of keys) {
    result[key] = obj[key];
  }
  return result;
}

// 呼び出し例
const user = { id: 1, name: "太郎", email: "t@example.com" };
const summary = pickFields(user, ["id", "name"]);
// pickFields(user, ["id", "age"]); // "age"が存在しないためコンパイルエラー

3-2. Conditional Types・infer・Template Literal Types

Conditional Types（T extends U ? X : Y）は「型レベルのif文」です。inferキーワードと組み合わせると、複雑な型から一部分だけを取り出せます。

conditional-types.ts
// 型レベルのif文
type IsString<T> = T extends string ? true : false;
type A = IsString<"hello">; // true
type B = IsString<42>;      // false

// infer: 関数の戻り値の型を取り出す（標準のReturnTypeの簡略版）
type MyReturnType<F> = F extends (...args: never[]) => infer R ? R : never;

function createUser() {
  return { id: 1, name: "太郎" };
}
type CreatedUser = MyReturnType<typeof createUser>;
// { id: number; name: string }

// Template Literal Types: 文字列の「形」を型で表現する
type EventName = `on${Capitalize<"click" | "hover" | "focus">}`;
// "onClick" | "onHover" | "onFocus"
💡
実務TipsTemplate Literal Typesは、CSSのプロパティ名やAPIのルーティングパス（`/users/${number}`など）を型として厳密に表現したいときに便利です。ただし複雑にしすぎるとコンパイルが遅くなることがあるので、使いどころは絞りましょう。
🤔
なぜこうなるのか型の世界にも「場合分け」が必要な場面があります(例: 配列ならその中身の型を、そうでなければそのままの型を使いたい)。inferは「まだ分からない部分」を一時的に名前を付けて置いておき、条件が成立したときにその名前で型を取り出すためのキーワードです。これがあることで、既存の複雑な型(関数の戻り値、配列の中身など)から必要な部分だけを抜き出す、汎用的な型ユーティリティを自分で組み立てられるようになります。
🎁
たとえ話福袋を思い浮かべてください。「もし箱の形が四角なら中身はぬいぐるみ、丸なら中身はお菓子」というルールがConditional Typesです。inferは、「開けてみないと分からない中身を、いったん『なぞの中身』というラベルを貼って置いておき、開けたときにそのラベルの名前で呼び出せるようにする」付箋のようなものです。

MODULE 04

非同期処理とエラーハンドリング

async/awaitの書き方自体はJavaScriptと同じですが、TypeScriptでは「戻り値の型」と「失敗した場合の型」まで設計するのがポイントです。

4-1. Promise・async/awaitの型付け

async関数の戻り値は自動的にPromise<T>にラップされます。Promise.allを使うと複数の非同期処理を並行に実行でき、それぞれの型がタプルとして正しく推論されます。

async-basics.ts
async function fetchUser(id: number): Promise<{ id: number; name: string }> {
  const res = await fetch(`/api/users/${id}`);
  if (!res.ok) {
    throw new Error(`failed to fetch user ${id}: ${res.status}`);
  }
  return res.json();
}

// 複数の非同期処理を並行実行し、それぞれの型が保たれる
async function loadDashboard(userId: number) {
  const [user, orders] = await Promise.all([
    fetchUser(userId),
    fetchOrders(userId),
  ]);
  // userは { id: number; name: string }、ordersはOrder[] として推論される
  return { user, orders };
}
⚠️
やりがちなミス複数の非同期処理をawaitを1つずつ直列に書くと、本来並行にできる処理まで直列化されて遅くなります。互いに依存しない処理はPromise.allでまとめましょう。
🤔
なぜこうなるのかawaitを1行ずつ並べると、1つ目の処理が終わるまで2つ目は絶対に始まりません。しかし2つの処理が互いの結果を必要としないなら、同時に始めても何の問題もないはずです。Promise.allは「みんな同時にスタートして、全員がゴールするまで待つ」という並行実行を、型情報(それぞれの戻り値の型)を保ったまま行うための仕組みです。依存関係がないのに直列に書くのは、待たなくていい時間をわざわざ待っているのと同じです。
🏃
たとえ話学校で「宿題を集める係」と「給食を配る係」が、本当は同時に作業できるのに、わざわざ「宿題を集め終わってから給食を配り始める」という順番を律儀に守っている状態を想像してください(直列)。実際は2つの係が同時に動けば、全体にかかる時間はぐっと短くなります(並行)。Promise.allは「よーい、ドン!」の合図でみんな一斉にスタートし、全員がゴールしたら次に進む、という笛の役割をしています。
EX 4-1-a

直列処理を並行処理に書き換える

応用

次のコードはfetchProfileとfetchSettingsが互いに依存していないのに直列実行されています。Promise.allを使って並行実行に書き換えてください。

async function loadPage(userId: number) {

  const settings = await fetchSettings(userId);

}
解答例を見る

タイムアウト付きfetchを実装する

発展

指定したミリ秒以内にレスポンスが返らなければError("timeout")で失敗するfetchWithTimeout(url: string, timeoutMs: number): Promise<Response>を、Promise.raceを使って実装してください。

解答例を見る 
function fetchWithTimeout(url: string, timeoutMs: number): Promise<Response> {
  const timeout = new Promise<never>((_, reject) => {
    setTimeout(() => reject(new Error("timeout")), timeoutMs);
  });

  return Promise.race([fetch(url), timeout]);
}

Promise<never>は「成功することはなく、必ず失敗する（または永遠に解決しない）」Promiseの戻り値の型です。Promise.raceの型推論と相性がよく使われます。

4-2. Result型パターンでの安全なエラーハンドリング

throwによる例外は、関数のシグネチャだけでは「何が失敗しうるか」が分かりません。Rustなどの言語で使われるResult型パターンをTypeScriptに輸入すると、成功/失敗を型として明示できます。

result.ts
type Result<T, E> =
  | { ok: true; value: T }
  | { ok: false; error: E };

function parseAge(input: string): Result<number, string> {
  const age = Number(input);
  if (Number.isNaN(age)) {
    return { ok: false, error: `"${input}" is not a number` };
  }
  if (age < 0 || age > 150) {
    return { ok: false, error: `${age} is out of valid range` };
  }
  return { ok: true, value: age };
}

// 呼び出し側は必ずok分岐を処理させられる
const result = parseAge("28");
if (result.ok) {
  console.log(result.value); // number
} else {
  console.error(result.error); // string
}
💡
実務Tipsフォームバリデーションのような「失敗が想定内」の処理はResult型で表現し、ネットワーク障害のような「本当に例外的な失敗」だけをthrowにする、と使い分けると呼び出し側のコードが読みやすくなります。
🤔
なぜこうなるのかthrowによる例外は、関数のシグネチャ(型)のどこにも「この関数はエラーを投げるかもしれない」という情報が現れません。呼び出す側はドキュメントを読むか、実際に動かして例外に遭遇するまで気づけないことがあります。Result型は「成功か失敗か」を戻り値の型そのものに組み込むので、呼び出し側はokによる分岐を書かない限りコンパイラに怒られる形になり、エラー処理の書き忘れを防げます。
🎰
たとえ話ガチャガチャを回すと、必ず「当たり」か「はずれ」のどちらかが出てきますよね。Result型は「必ずこのどちらかの結果が返ってくるよ」と保証してくれる仕組みです。一方throwは「たまに何の前触れもなく機械が止まって、何も出てこなくなる」ようなもので、受け取る側はいつ止まるか分からないまま身構えていないと対応できません。
EX 4-2-a

メールアドレスのバリデーションをResult型で書く

基礎確認

「@を含む」という簡易ルールでメールアドレスを検証するvalidateEmail(input: string): Result<string, string>を実装してください。成功時は入力値をそのままvalueとして返します。

解答例を見る 
function validateEmail(input: string): Result<string, string> {
  if (!input.includes("@")) {
    return { ok: false, error: "メールアドレスの形式が正しくありません" };
  }
  return { ok: true, value: input };
}
EX 4-2-b

複数のResultを合成するcombineを実装する

発展

Result<T, E>の配列を受け取り、すべて成功していれば{ ok: true, value: T[] }を、1つでも失敗していれば最初のエラーを{ ok: false, error: E }として返すcombine<T, E>(results: Result<T, E>[]): Result<T[], E>を実装してください。

解答例を見る 
function combine<T, E>(results: Result<T, E>[]): Result<T[], E> {
  const values: T[] = [];
  for (const result of results) {
    if (!result.ok) {
      return result; // { ok: false; error: E } をそのまま返す
    }
    values.push(result.value);
  }
  return { ok: true, value: values };
}

フォームの複数フィールドを一括バリデーションするときなどに、このcombineのような関数が役立ちます。

5-1. Discriminated Unionとブランド型

Discriminated Union（タグ付き合併型）は、共通の「タグ用プロパティ（kindやtypeなど）」を持つ複数の型を1つのUnionにまとめるパターンです。UIの状態管理（ローディング/成功/失敗）で頻出します。

discriminated-union.ts
type FetchState<T> =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: T }
  | { status: "error"; message: string };

function render<T>(state: FetchState<T>): string {
  switch (state.status) {
    case "idle": return "待機中";
    case "loading": return "読み込み中...";
    case "success": return `取得成功: ${JSON.stringify(state.data)}`;
    case "error": return `エラー: ${state.message}`;
  }
}
🤔
なぜこうなるのか複数の「かもしれない状態」をバラバラの型で扱うと、それぞれの状態にどんなプロパティがあるかを呼び出し側が毎回覚えておく必要があります。共通のstatusのようなタグを持つUnionにまとめておくと、switchで分岐した瞬間、その分岐の中で「今はdataが確実に存在する」「今はmessageが確実に存在する」とコンパイラが自動的に絞り込んでくれます。状態ごとに必要な情報が変わるUIの実装(ローディング中/成功/失敗)と、この仕組みは非常に相性がよいのです。
🚦
たとえ話信号機を思い浮かべてください。「赤・黄・青」という共通の分類(statusのようなタグ)があって、それぞれの色ごとに「止まれ」「注意」「進め」という決まった意味が紐づいています。Discriminated Unionは、まさにこの「タグを見れば、そのあとに続く情報の中身が自動的に分かる」という仕組みをプログラムの型として表現したものです。

ブランド型は「見た目は同じ型（例: numberやstring）だが、意味的には別物」を区別するテクニックです。UserIdとProductIdを両方numberで扱っていると、引数の渡し間違いをコンパイラが検出できません。

branded-types.ts
type UserId = number & { readonly __brand: "UserId" };
type ProductId = number & { readonly __brand: "ProductId" };

function toUserId(id: number): UserId {
  return id as UserId;
}

function getUser(id: UserId) { /* ... */ }

const userId = toUserId(1);
const productId = 1 as unknown as ProductId;

getUser(userId);    // OK
// getUser(productId); // コンパイルエラー: ProductIdはUserIdではない
// getUser(1);          // コンパイルエラー: ただのnumberも受け付けない
🤔
なぜこうなるのかUserIdもProductIdも、実体はどちらもただのnumberです。TypeScriptの型システムは「構造が同じなら同じ型として扱う」という考え方(構造的型付け)が基本なので、何も工夫しなければProductIdの値をUserIdが必要な場所に渡せてしまいます。ブランド型は、実在しない__brandという目印のプロパティを型だけに追加することで、「構造は同じでも意味が違う」ことを人工的にコンパイラへ教える工夫です。
🔑
たとえ話見た目が全く同じ鍵が2本あるとします(どちらもnumberという意味)。でも実際には「家の鍵」と「車の鍵」で使い道が違いますよね。ブランド型は、見た目は同じ鍵でも「これは家専用」「これは車専用」という刻印を付けておくようなものです。間違えて車の鍵で家を開けようとしたら、刻印を見た瞬間に「これは違う鍵だ」とすぐに気づけます。

5-2. 型安全なAPIクライアント設計

APIのエンドポイントごとにレスポンス型がバラバラだと、呼び出し側で型の対応関係を手動で管理することになります。「エンドポイント名から戻り値の型を導く」設計にしておくと、型の対応漏れをコンパイラがチェックしてくれます。

api-client.ts
// エンドポイントと戻り値の型を1つのマップで管理する
type ApiRoutes = {
  "/users": { id: number; name: string }[];
  "/users/me": { id: number; name: string; email: string };
  "/products": { id: number; price: number }[];
};

async function apiGet<Path extends keyof ApiRoutes>(
  path: Path
): Promise<ApiRoutes[Path]> {
  const res = await fetch(path as string);
  return res.json();
}

// 呼び出し側は文字列を書くだけで、戻り値の型が自動的に確定する
const users = await apiGet("/users");       // { id: number; name: string }[]
const me = await apiGet("/users/me");       // { id: number; name: string; email: string }
// const bad = await apiGet("/unknown");    // コンパイルエラー: ApiRoutesに存在しないパス
💡
実務Tipsこの設計はtRPCやOpenAPIから型を自動生成するツールの考え方の基礎にもなっています。エンドポイントが増えるほど「型マップに1行追加するだけで型安全になる」メリットが大きくなります。
🤔
なぜこうなるのかエンドポイントごとに戻り値の型をその都度手動で管理していると、サーバー側の仕様が変わったときにクライアント側の型を直し忘れても誰も気づけません。実行して初めて「想定と違うデータが来た」と気づくことになります。1つの型マップ(ApiRoutes)にパスと戻り値の対応をまとめておけば、パスを指定した瞬間に戻り値の型が自動的に決まり、存在しないパスへのアクセスもコンパイル時にエラーとして検出できます。
🍽️
たとえ話レストランのメニュー表を思い浮かべてください。メニュー表(ApiRoutes)に「オムライスを頼んだらオムライスが出てくる」とはっきり書いてあれば、注文する人もお店の人も迷いません。もしメニュー表がなく、口頭で毎回「これ頼んだら何が出てくるんだっけ?」と確認しないといけないとしたら、注文ミスや行き違いが起きやすくなりますよね。

クラス・モジュール設計とNode.js実務

TypeScriptのクラス機能と、プロジェクト全体の型安全性を支える設定まわりを扱います。

6-1. 抽象クラス・インターフェース設計

interfaceは「形」だけを定義し実装を持てません。abstract classは共通実装を持ちつつ、一部を子クラスに実装させられます。「共通処理があるならabstract class、契約だけ決めたいならinterface」が基本方針です。

abstract-class.ts
abstract class PaymentProcessor {
  // 共通のテンプレート処理
  process(amount: number): void {
    this.validate(amount);
    this.charge(amount);
    console.log(`${amount}円の決済が完了しました`);
  }

  protected validate(amount: number): void {
    if (amount <= 0) throw new Error("amount must be positive");
  }

  // サブクラスに実装を強制する
  protected abstract charge(amount: number): void;
}

class CreditCardProcessor extends PaymentProcessor {
  protected charge(amount: number): void {
    console.log(`クレジットカードで${amount}円を課金`);
  }
}

class CreditCardProcessor2 extends PaymentProcessor {
  protected charge(amount: number): void {
    console.log(`コンビニ決済で${amount}円を課金`);
  }
}
💡
実務TipsこれはJavaのTemplate Methodパターンと同じ考え方です。共通の処理の流れ（validate → charge → ログ出力）を親クラスで固定し、可変な部分だけをサブクラスに実装させることで、処理の流れの一貫性を保証できます。
🤔
なぜこうなるのかinterfaceは「形(契約)だけ」を決めるので、継承関係がまったく無関係なクラス同士にも横断的に同じ約束を持たせられます。abstract classは共通の処理そのもの(実装コード)を持てるので、同じ手順を毎回コピペする必要がなくなり、手順の一部を直したいときも親クラス1箇所を直すだけで済みます。「契約だけ決めたいか、処理そのものを共有したいか」で使い分けるのが基本です。
🍛
たとえ話interfaceは「電池で動くおもちゃはみんな乾電池のサイズが同じ」という「規格」だけを決めるルールです。中身がロボットでも車でも構いません。abstract classは「カレーの作り方のレシピ」のようなもので、「野菜を切る→炒める→煮込む」という流れは全部共通、「何のルウを使うか」だけを各家庭(サブクラス)が自由に選べる、というイメージです。
EX 6-1-a

通知の抽象クラスを設計する

応用

共通処理として「送信前にログを出す」→「送信する」→「送信後にログを出す」という流れを持つabstract class Notifierを実装してください。実際の送信処理（protected abstract deliver(message: string): void）だけをサブクラスEmailNotifierで実装してください。

解答例を見る 
abstract class Notifier {
  send(message: string): void {
    console.log(`[send開始] ${message}`);
    this.deliver(message);
    console.log(`[send完了] ${message}`);
  }

  protected abstract deliver(message: string): void;
}

class EmailNotifier extends Notifier {
  protected deliver(message: string): void {
    console.log(`メール送信: ${message}`);
  }
}
EX 6-1-b

interfaceとabstract classを使い分ける

基礎確認

「複数の無関係なクラスに共通の振る舞い（例: Comparableのような比較機能）だけを持たせたい」場合と、「共通のロジックを1箇所にまとめて重複をなくしたい」場合、それぞれinterfaceとabstract classのどちらが適しているか、理由とあわせて答えてください。

解答例を見る

前者（共通の振る舞いだけを持たせたい）はinterfaceが適しています。TypeScriptのクラスは複数のinterfaceを実装できるため、無関係な継承階層のクラスにも横断的に「契約」を持たせられます。後者（共通ロジックをまとめたい）はabstract classが適しています。実装コードそのものを共有でき、テンプレートメソッドパターンのような「流れの固定」も表現できます。

6-2. モジュール分割とtsconfig実務Tips

型定義は「使う場所の近く」ではなく「意味のまとまり」でファイルを分けると、プロジェクトが大きくなっても迷子になりません。よくある構成は次の通りです。

project-structure.txt
src/
  types/
    user.ts        // ドメインの型定義（User, UserId など）
    api.ts         // API通信共通の型（ApiResponse<T> など）
  services/
    user-service.ts
  utils/
    result.ts      // Result<T, E> など汎用の型・関数

実務でまず有効化すべきtsconfig.jsonのオプションは次の3つです。これらをオフにしたまま開発すると、TypeScriptの型チェックの恩恵の多くが失われます。

オプション効果
strict厳格な型チェックをまとめて有効化する（実質必須）
noUncheckedIndexedAccessarr[i]やobj[key]の結果にundefinedの可能性を含める
noImplicitOverride親クラスのメソッドを上書きする際にoverrideを必須にし、タイプミスによる意図しない新規メソッド化を防ぐ
⚠️
やりがちなミスnoUncheckedIndexedAccessを有効にしていないと、const first = arr[0]は要素が存在しなくてもundefinedを許容しない型になり、実行時エラーの温床になります。新規プロジェクトでは最初からオンにしておきましょう。
🤔
なぜこうなるのかstrict系のオプションをオフにしたままだと、TypeScriptは「型を書いてはいるけれど、実質的にはJavaScriptとほとんど変わらない緩いチェック」しかしてくれません。noUncheckedIndexedAccessのようなオプションは、「配列の範囲外アクセス」という実務で本当によく起きるバグの種を、実行前のコンパイル段階で検出できるようにしてくれます。オプションをオンにする一手間が、本番環境での思わぬundefinedエラーを大きく減らします。
🔍
たとえ話strictモードをオンにするのは、先生に「答案を隅から隅までちゃんとチェックしてね」とお願いするようなものです。オフのままだと、先生は大きな間違いしか見てくれず、細かい見落とし(空の箱から何かを取り出そうとするような小さなミス)を見逃してしまいます。厳しくチェックしてもらったほうが、本番でのテスト(実行)前にミスに気づけますよね。
EX 6-2-a

noUncheckedIndexedAccessの効果を説明する

基礎確認

次のコードはnoUncheckedIndexedAccessが有効な場合、なぜコンパイルエラーになるか説明し、安全な書き方に直してください。

function firstChar(items: string[]): string {
  return items[0].charAt(0); // items[0]がundefinedの可能性
}
解答例を見る

理由: itemsが空配列の場合、items[0]は実行時にundefinedになりますが、noUncheckedIndexedAccessを付けないTypeScriptはこれを型上考慮しません。有効にするとitems[0]の型はstring | undefinedとなり、.charAtの呼び出しがコンパイルエラーになります。

function firstChar(items: string[]): string {
  const first = items[0];
  if (first === undefined) {
    throw new Error("items is empty");
  }
  return first.charAt(0);
}
EX 6-2-b

overrideキーワードでタイプミスを防ぐ

応用

次のコードには「親クラスのメソッドをオーバーライドしたつもりが、メソッド名のタイプミスで新しいメソッドを追加してしまっている」バグがあります。noImplicitOverrideが有効ならどちらの行がコンパイルエラーになるか指摘し、正しいコードに直してください。

abstract class Notifier {
  abstract deliver(message: string): void;
}

class SmsNotifier extends Notifier {
  delvier(message: string): void { // "deliver" のタイプミス
    console.log(`SMS: ${message}`);
  }
}
解答例を見る

delvierはdeliverのタイプミスで、抽象メソッドをオーバーライドできておらず、無関係な新メソッドとして定義されてしまっています。overrideキーワードを付けると、対応する親クラスのメンバーが存在しない場合にコンパイルエラーとして検出できます。

class SmsNotifier extends Notifier {
  override deliver(message: string): void {
    console.log(`SMS: ${message}`);
  }
}
