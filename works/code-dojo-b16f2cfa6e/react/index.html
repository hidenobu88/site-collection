MODULE 01

Hooksの応用

useState・useEffectは書けて当然、という前提で「なぜその書き方が安全なのか」を掘り下げます。

1-1. useStateの設計パターン

直前の状態を使って更新する場合は、必ず関数形式の更新を使います。setCount(count + 1)は「今読んでいるcount」を使うため、連続で呼び出すとバッチ処理により意図しない結果になることがあります。

Counter.tsx
function Counter() {
  const [count, setCount] = useState(0);

  function handleTripleClick() {
    // NG: 3回呼んでも +1 にしかならないことがある
    // setCount(count + 1);
    // setCount(count + 1);
    // setCount(count + 1);

    // OK: 常に最新の状態を受け取って更新する
    setCount((prev) => prev + 1);
    setCount((prev) => prev + 1);
    setCount((prev) => prev + 1);
  }

  return <button onClick={handleTripleClick}>count: {count}</button>;
}

また、複数の関連するstateはオブジェクトにまとめるべきか、それとも別々のuseStateに分けるべきか迷うところです。目安は「同時に更新されることが多いか」です。

// 良い例: xとyは常にセットで更新されるのでオブジェクトにまとめる
const [position, setPosition] = useState({ x: 0, y: 0 });

// 良い例: nameとisLoadingは無関係な頻度で更新されるので分ける
const [name, setName] = useState("");
const [isLoading, setIsLoading] = useState(false);
⚠️
やりがちなミスオブジェクトのstateを更新するとき、setPosition({ x: 10 })のように書くとyが消えてしまいます。useStateの更新はマージではなく置き換えなので、setPosition((prev) => ({ ...prev, x: 10 }))のようにスプレッドで既存の値を保持する必要があります。
🤔
なぜこうなるのかsetCount(count + 1)のcountは、そのイベントハンドラが呼ばれた瞬間に確定した「そのときの値」であり、Reactは複数の更新をまとめて処理する（バッチ処理）ため、3回連続で呼んでも同じ古いcountを使った「同じ計算」を3回行うだけになりがちです。関数形式の(prev) => prev + 1は、実際に適用される直前の最新の値を毎回受け取るため、連続で呼んでも正しく積み上がります。
🖊️
たとえ話黒板に書いてある数字を、3人が同時に「今の数字に1を足して書き直して」と頼まれた場面を想像してください。3人とも「黒板に書いてある今の数字(たとえば3)」を最初に見てから、それぞれ同時に4と書き込んでしまうと、3回頼んでも結局4のままです。それより「今書いてある数字が何であれ、それに1を足してね」というやり方なら、1人ずつ確実に処理されて3回分ちゃんと増えていきます。(prev) => prev + 1は、まさにこの後者のやり方です。
EX 1-1-a

非同期処理後のカウントアップを安全に書く

基礎確認

ボタンを押すと1秒後にcountを+1するDelayedCounterコンポーネントを、関数形式の更新を使って実装してください（setTimeoutを使用）。

解答例を見る 
function DelayedCounter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setTimeout(() => {
      setCount((prev) => prev + 1);
    }, 1000);
  }

  return <button onClick={handleClick}>count: {count}</button>;
}

もしsetCount(count + 1)と書いていた場合、1秒の間にボタンを連打すると、クロージャに閉じ込められた古いcountを元に計算してしまい、正しく加算されません。

EX 1-1-b

オブジェクトstateの部分更新フォームを実装する

応用

{ name: string; email: string }を1つのuseStateで管理し、name用とemail用の2つの<input>から、それぞれ他方の値を消さずに更新できるフォームコンポーネントを実装してください。

解答例を見る 
function ProfileForm() {
  const [form, setForm] = useState({ name: "", email: "" });

  function updateField<K extends keyof typeof form>(key: K, value: string) {
    setForm((prev) => ({ ...prev, [key]: value }));
  }

  return (
    <form>
      <input
        value={form.name}
        onChange={(e) => updateField("name", e.target.value)}
      />
      <input
        value={form.email}
        onChange={(e) => updateField("email", e.target.value)}
      />
    </form>
  );
}

1-2. useEffectの依存配列とクリーンアップ

useEffectは「Reactの外の世界と同期する」ための仕組みです。依存配列（第2引数）は「このEffectが再実行される条件」であり、ESLintのreact-hooks/exhaustive-depsが警告する項目は基本的にすべて含めるべきです。

SearchBox.tsx
function SearchResults({ query }: { query: string }) {
  const [results, setResults] = useState<string[]>([]);

  useEffect(() => {
    let cancelled = false;

    async function fetchResults() {
      const res = await fetch(`/api/search?q=${query}`);
      const data = await res.json();
      if (!cancelled) {
        setResults(data);
      }
    }
    fetchResults();

    // クリーンアップ: 古いリクエストの結果を反映させない
    return () => {
      cancelled = true;
    };
  }, [query]); // queryが変わるたびに再実行

  return (
    <ul>
      {results.map((r) => <li key={r}>{r}</li>)}
    </ul>
  );
}
⚠️
やりがちなミスcancelledフラグを立てずにsetResultsだけ呼んでいると、「Aの検索結果を取得中にBに検索し直した」場合、Aのレスポンスが後から返ってきてBの結果を上書きしてしまう競合状態（レースコンディション）が起こります。
🤔
なぜこうなるのかuseEffectは「Reactの外側の世界（通信・タイマー・DOM操作など）と同期する」ための仕組みです。依存配列は「このEffectが何に基づいて動いているか」の宣言であり、含めるべき値を省略すると、Reactはその値が変わったことに気づかず、古い情報のままEffectを動かし続けてしまいます。クリーンアップ関数は「次のEffectが始まる前に、前回のEffectの後片付けをする」ための仕組みで、これが無いと、先に投げた古いリクエストの結果が、後から届いた新しい結果を上書きしてしまうことがあります。
📮
たとえ話図書館で本を借りるとき、欲しい本のタイトルが変わったら、もう一度違う本を借りに行き直しますよね(依存配列にqueryを入れる)。もし「最初に頼んだタイトル」だけをずっと覚えていて二度と確認しないと(空の依存配列)、いつまでも最初の古い本のことしか気にかけられません。クリーンアップは、新しい本を借りに行く前に「今借りている本を返却する」作業です。返却せずに何冊も借り続けると、後から届いた本が先に届いた古い本に上書きされてしまうような混乱が起きます。
EX 1-2-a

イベントリスナーの登録と解除を実装する

基礎確認

ウィンドウ幅を追跡するuseEffectを持つWindowWidthコンポーネントを実装してください。window.addEventListener("resize", ...)で監視し、アンマウント時に必ずremoveEventListenerでクリーンアップしてください。

解答例を見る 
function WindowWidth() {
  const [width, setWidth] = useState(window.innerWidth);

  useEffect(() => {
    function handleResize() {
      setWidth(window.innerWidth);
    }
    window.addEventListener("resize", handleResize);
    return () => {
      window.removeEventListener("resize", handleResize);
    };
  }, []); // マウント時に1回だけ登録

  return <p>幅: {width}px</p>;
}
EX 1-2-b

依存配列の不足バグを見つける

応用

次のコードには依存配列の不足によるバグがあります。何が問題か指摘し、修正してください。

function UserGreeting({ userId }: { userId: number }) {
  const [name, setName] = useState("");

  useEffect(() => {
    fetchUserName(userId).then(setName);
  }, []); // userIdが依存配列に無い

  return <p>こんにちは、{name}さん</p>;
}
解答例を見る

問題点: userIdが変わって親コンポーネントから別のユーザーが指定されても、Effectが再実行されず、最初にマウントされたときのuserIdの名前が表示され続けます。

useEffect(() => {
  fetchUserName(userId).then(setName);
}, [userId]); // userIdの変化を検知して再実行する

MODULE 02

レンダリング最適化

「とりあえずuseMemoを付ける」は多くの場合逆効果です。何がどう再計算・再レンダリングされているかを理解してから最適化しましょう。

2-1. useMemo・useCallbackの正しい使い所

useMemoとuseCallbackは「再計算・再生成のコストが高い場合」または「値の同一性（参照）を保つ必要がある場合（memo化した子への props や、依存配列に渡す関数など）」に使うのが基本です。単純な計算にまで乱用すると、メモ化自体のコストで逆に遅くなることもあります。

ExpensiveList.tsx
function ProductList({ products, keyword }: { products: Product[]; keyword: string }) {
  // 重い処理（大量データのフィルタ・ソート）はuseMemoの好例
  const filtered = useMemo(() => {
    return products
      .filter((p) => p.name.includes(keyword))
      .sort((a, b) => b.price - a.price);
  }, [products, keyword]);

  return (
    <ul>
      {filtered.map((p) => <li key={p.id}>{p.name}</li>)}
    </ul>
  );
}
SearchInput.tsx
function SearchInput({ onSearch }: { onSearch: (q: string) => void }) {
  const [query, setQuery] = useState("");

  // memo化した子コンポーネントに関数を渡すときは useCallback で参照を安定させる
  const handleSearch = useCallback(() => {
    onSearch(query);
  }, [query, onSearch]);

  return (
    <>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      <SearchButton onClick={handleSearch} />
    </>
  );
}

const SearchButton = memo(function SearchButton({ onClick }: { onClick: () => void }) {
  return <button onClick={onClick}>検索</button>;
});
💡
実務Tips「このコンポーネントが遅い」と体感する前に最適化するのはコストに見合わないことが多いです。React DevTools Profilerで実際に再レンダリングのコストを計測してから、必要な箇所にだけメモ化を入れましょう。
🤔
なぜこうなるのかuseMemoやuseCallback自体にも「前回の依存値と今回の依存値を比較する」というコストがかかります。ごく軽い計算にまでメモ化を付けると、その比較コストのほうが計算そのもののコストより高くつき、かえって遅くなることさえあります。メモ化が本当に効果を発揮するのは「計算そのものが重い場合」か「参照の同一性が重要な場合(memo化した子コンポーネントへのpropsなど)」に限られます。
➕
たとえ話「2+2」のような簡単な足し算をするたびに、「あれ、これ前にも計算したっけ?」とメモを確認する手間をかけるのは、逆に面倒ですよね。それより毎回サッと計算したほうが速いです。でも、何百人ものテストの点数をきれいに並べ替える(重い処理)場合は、「同じデータならもう一度並べ替えなくていいよ」と覚えておく(メモ化)ことに、はっきりとした意味が出てきます。
EX 2-1-a

合計金額の計算をuseMemoで最適化する

基礎確認

items: { price: number; quantity: number }[]を受け取り、合計金額を表示するCartTotalコンポーネントで、合計金額の計算をuseMemoでメモ化してください（itemsが変わらない限り再計算しない）。

解答例を見る 
function CartTotal({ items }: { items: { price: number; quantity: number }[] }) {
  const total = useMemo(() => {
    return items.reduce((sum, item) => sum + item.price * item.quantity, 0);
  }, [items]);

  return <p>合計: {total}円</p>;
}
EX 2-1-b

不要なuseMemoを見つけて削除する

応用

次のコードのuseMemoは、実は不要（むしろ有害に近い）です。理由を説明し、シンプルな書き方に直してください。

function Greeting({ name }: { name: string }) {
  const message = useMemo(() => `こんにちは、${name}さん`, [name]);
  return <p>{message}</p>;
}
解答例を見る

理由: 文字列の結合は極めて軽量な処理であり、useMemoによるメモ化・依存配列の比較コストの方が上回ります。「重い計算・大きなデータ構造の生成」以外では、素直に毎回計算した方がシンプルで速いことがほとんどです。

function Greeting({ name }: { name: string }) {
  const message = `こんにちは、${name}さん`;
  return <p>{message}</p>;
}

2-2. React.memoと不要な再レンダリング防止

親コンポーネントが再レンダリングされると、子コンポーネントも（原則として）連鎖的に再レンダリングされます。memoは「propsが（浅い比較で）変わっていなければ再レンダリングをスキップする」仕組みです。

memo-demo.tsx
const ExpensiveRow = memo(function ExpensiveRow({ user }: { user: User }) {
  console.log("render:", user.name); // propsが変わらなければ呼ばれない
  return <tr><td>{user.name}</td></tr>;
});

function UserTable({ users }: { users: User[] }) {
  const [filter, setFilter] = useState("");

  return (
    <>
      <input value={filter} onChange={(e) => setFilter(e.target.value)} />
      <table>
        <tbody>
          {users.map((u) => <ExpensiveRow key={u.id} user={u} />)}
        </tbody>
      </table>
    </>
  );
}
⚠️
やりがちなミスmemoで子をラップしても、親がその都度{ ... }や() => {}のようなオブジェクト・関数リテラルをpropsとして渡していると、毎回「新しい参照」が生成されるためmemoの浅い比較は必ず「変化あり」と判定します。useMemo/useCallbackとセットで初めて効果を発揮します。
🤔
なぜこうなるのかReactは親が再レンダリングされると、原則として子も連鎖的に再レンダリングします。memoは「propsが(浅い比較で)変わっていなければ、その手間をスキップする」仕組みです。しかし、オブジェクトや関数のリテラルをその場で作って渡すと、中身が同じでも「新しく作られた別のもの」として扱われるため、比較は必ず「変わった」と判定されてしまいます。だからuseMemo/useCallbackで参照そのものを安定させて初めて、memoは本来の効果を発揮できます。
🍱
たとえ話双子のきょうだいが毎日全く同じメニューのお弁当を持ってきているのに、先生が「昨日と同じお弁当かな?」を、中身を1つずつ確認するのではなく「同じお弁当箱かどうか」だけで判断しているとします。メニューが同じでも、毎回新しいお弁当箱に詰め替えて持ってきたら、先生は「違う箱だ、変わった!」と勘違いしてしまいます。中身が同じなら同じお弁当箱を使い回す(useMemo/useCallbackで参照を保つ)ことで、先生は正しく「変わっていない」と気づけるのです。
EX 2-2-a

memoが効かない原因を直す

応用

次のParentはfilterを更新するたびにExpensiveChild（memo化済み）が毎回再レンダリングされてしまいます。原因を指摘し、修正してください。

const ExpensiveChild = memo(function ExpensiveChild({ onSave }: { onSave: () => void }) {
  console.log("render ExpensiveChild");
  return <button onClick={onSave}>保存</button>;
});

function Parent() {
  const [filter, setFilter] = useState("");

  return (
    <>
      <input value={filter} onChange={(e) => setFilter(e.target.value)} />
      <ExpensiveChild onSave={() => console.log("saved")} />
    </>
  );
}
解答例を見る

原因: onSave={() => console.log("saved")}はParentが再レンダリングされるたびに新しい関数（新しい参照）が作られるため、memoの浅い比較が常に「変化あり」と判定してしまいます。

function Parent() {
  const [filter, setFilter] = useState("");

  const handleSave = useCallback(() => {
    console.log("saved");
  }, []); // 依存がないので常に同じ参照を維持する

  return (
    <>
      <input value={filter} onChange={(e) => setFilter(e.target.value)} />
      <ExpensiveChild onSave={handleSave} />
    </>
  );
}
EX 2-2-b

カスタム比較関数を持つmemoを実装する

発展

user: { id: number; name: string; lastLoginAt: Date }をpropsに持つUserBadgeコンポーネントを、「idとnameが同じならlastLoginAtが変わっても再レンダリングしない」ようにカスタム比較関数付きのmemoで実装してください。

ヒント: memo(Component, areEqual)の第2引数で、propsを比較する関数を渡せます。
解答例を見る 
type UserBadgeProps = { user: { id: number; name: string; lastLoginAt: Date } };

const UserBadge = memo(
  function UserBadge({ user }: UserBadgeProps) {
    return <span>{user.name}</span>;
  },
  (prevProps, nextProps) => {
    // trueを返すと「等しい＝再レンダリング不要」
    return (
      prevProps.user.id === nextProps.user.id &&
      prevProps.user.name === nextProps.user.name
    );
  }
);
✅ モジュール2完了の目安: メモ化が効かなくなるパターン（新しい参照の生成）を説明できればOKです。
MODULE 03

カスタムフック設計

似たようなuseState/useEffectの組み合わせをコンポーネント間でコピペしていたら、カスタムフックに切り出すサインです。

3-1. ロジックを切り出すカスタムフック

カスタムフックは「useから始まる、Hooksを内部で使う普通の関数」です。UIを持たず、状態とロジックだけを再利用可能な形にまとめられます。

useToggle.ts
function useToggle(initial = false) {
  const [value, setValue] = useState(initial);

  const toggle = useCallback(() => setValue((v) => !v), []);
  const setTrue = useCallback(() => setValue(true), []);
  const setFalse = useCallback(() => setValue(false), []);

  return { value, toggle, setTrue, setFalse } as const;
}

// 呼び出し側
function Modal() {
  const { value: isOpen, setTrue: open, setFalse: close } = useToggle(false);
  return (
    <>
      <button onClick={open}>開く</button>
      {isOpen && <div className="modal">モーダルの中身 <button onClick={close}>閉じる</button></div>}
    </>
  );
}
💡
実務Tips返り値をオブジェクトにするか配列にするかは、「呼び出し側で名前を変えたいか」で判断します。useStateのように必ず2つセットで分割代入するものは配列、useToggleのように一部だけ使うことが多いものはオブジェクトが向いています。
🤔
なぜこうなるのか似たようなuseStateとuseEffectの組み合わせを複数のコンポーネントにコピペしていると、片方にバグ修正を入れてもコピペ先すべてには反映されず、直し忘れが生まれます。カスタムフックに切り出すと「ロジックの本体は1箇所」になり、修正は1箇所で済み、コンポーネント自体は「見た目の表示」に専念できるようになります。
📖
たとえ話給食当番の手順(配膳して、片付ける)を、クラスごとに先生がそれぞれ独自のメモに書いて教えているとします。手順が1つ変わるたびに、全クラスの先生のメモを1枚ずつ書き直して回らないといけません。それより「給食当番マニュアル」を1つだけ作って、みんながそれを見るようにすれば、変更はマニュアル1つを直すだけで済みます。カスタムフックは、まさにこの「共通マニュアル」の役割を果たします。
EX 3-1-a

localStorageと同期するuseLocalStorageを実装する

応用

useStateと同じ使い勝手で、値の変更が自動的にlocalStorageにも保存されるuseLocalStorage<T>(key: string, initialValue: T)を実装してください（[value, setValue]のタプルを返します）。

解答例を見る 
function useLocalStorage<T>(key: string, initialValue: T) {
  const [value, setValue] = useState<T>(() => {
    const stored = window.localStorage.getItem(key);
    return stored ? (JSON.parse(stored) as T) : initialValue;
  });

  useEffect(() => {
    window.localStorage.setItem(key, JSON.stringify(value));
  }, [key, value]);

  return [value, setValue] as const;
}

// 呼び出し例
const [theme, setTheme] = useLocalStorage("theme", "light");

useStateの初期値に関数（遅延初期化）を渡すことで、localStorageの読み取りが初回レンダリング時にしか実行されない点がポイントです。

入力値の変化から一定時間（delayMs）操作がなければ確定値を更新するuseDebouncedValue<T>(value: T, delayMs: number): Tを実装してください。検索ボックスの入力中に毎回APIを叩かないようにする用途を想定しています。

解答例を見る 
function useDebouncedValue<T>(value: T, delayMs: number): T {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const timer = setTimeout(() => {
      setDebounced(value);
    }, delayMs);

    return () => clearTimeout(timer); // 値が変わったら前のタイマーをキャンセル
  }, [value, delayMs]);

  return debounced;
}

// 呼び出し例
function SearchBox() {
  const [query, setQuery] = useState("");
  const debouncedQuery = useDebouncedValue(query, 400);

  useEffect(() => {
    if (debouncedQuery) fetchSearchResults(debouncedQuery);
  }, [debouncedQuery]);

  return <input value={query} onChange={(e) => setQuery(e.target.value)} />;
}

3-2. データ取得用カスタムフックの設計

データ取得のロジック（ローディング・成功・失敗の管理、キャンセル処理）は、コンポーネントごとに書くとどうしても重複します。Discriminated Unionの状態表現（TypeScript講座モジュール5参照）と組み合わせると、扱いやすいカスタムフックになります。

useFetch.ts
type FetchState<T> =
  | { status: "loading" }
  | { status: "success"; data: T }
  | { status: "error"; error: Error };

function useFetch<T>(url: string): FetchState<T> {
  const [state, setState] = useState<FetchState<T>>({ status: "loading" });

  useEffect(() => {
    let cancelled = false;
    setState({ status: "loading" });

    fetch(url)
      .then((res) => {
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        return res.json();
      })
      .then((data: T) => {
        if (!cancelled) setState({ status: "success", data });
      })
      .catch((error: Error) => {
        if (!cancelled) setState({ status: "error", error });
      });

    return () => {
      cancelled = true;
    };
  }, [url]);

  return state;
}

// 呼び出し側
function UserProfile({ userId }: { userId: number }) {
  const state = useFetch<User>(`/api/users/${userId}`);

  if (state.status === "loading") return <p>読み込み中...</p>;
  if (state.status === "error") return <p>エラー: {state.error.message}</p>;
  return <p>{state.data.name}</p>;
}
💡
実務Tips実務では自前実装よりも、キャッシュ・再取得・重複排除まで面倒を見てくれるTanStack Query（旧React Query）やSWRを使うのが一般的です。ただしそれらのライブラリの内部でも、ここで学んだ「状態の型設計」と同じ考え方が使われています。
🤔
なぜこうなるのかデータ取得には「読み込み中/成功/失敗」という共通のパターンと、「コンポーネントが先に別の対象を表示し直したときに、古いレスポンスで新しい状態を上書きしてしまう」という共通の落とし穴があります。これを毎回コンポーネントごとに書いていると、対応漏れが起きやすくなります。1つのカスタムフックにこの「型で表現された状態遷移」をまとめておけば、データ取得を行うすべての場所で同じ安全さが自動的に保証されます。
📦
たとえ話宅配便を注文するたびに、「届くまで待つ→届いたか確認する→もし業者が来る前に引っ越したら受け取りをキャンセルする」という手順を毎回一から考えるのは大変です。宅配ロッカーのような「共通の受け取りシステム」を1つ用意しておけば(カスタムフック)、何を注文しても同じ安全な手順で受け取れて、引っ越し(古いリクエストのキャンセル)も自動でやってくれます。

MODULE 04

状態管理設計

stateが増えて更新ロジックが複雑になったら、状態遷移を1箇所にまとめる設計に切り替えるタイミングです。

4-1. useReducerによる複雑な状態管理

1つのstateに対して「複数の更新パターン（アクション）」があり、それぞれの更新ロジックが絡み合っている場合、useReducerで「アクションの種類ごとに状態遷移を1箇所にまとめる」と見通しが良くなります。

cartReducer.ts
type CartItem = { id: number; name: string; quantity: number };
type CartState = { items: CartItem[] };

type CartAction =
  | { type: "ADD_ITEM"; item: CartItem }
  | { type: "REMOVE_ITEM"; id: number }
  | { type: "CHANGE_QUANTITY"; id: number; quantity: number }
  | { type: "CLEAR" };

function cartReducer(state: CartState, action: CartAction): CartState {
  switch (action.type) {
    case "ADD_ITEM":
      return { items: [...state.items, action.item] };
    case "REMOVE_ITEM":
      return { items: state.items.filter((i) => i.id !== action.id) };
    case "CHANGE_QUANTITY":
      return {
        items: state.items.map((i) =>
          i.id === action.id ? { ...i, quantity: action.quantity } : i
        ),
      };
    case "CLEAR":
      return { items: [] };
  }
}

function Cart() {
  const [state, dispatch] = useReducer(cartReducer, { items: [] });

  return (
    <button onClick={() => dispatch({ type: "CLEAR" })}>
      カートを空にする
    </button>
  );
}
💡
実務TipsDiscriminated Unionでアクション型を定義しておくと、switch文のそれぞれのcase内でactionのプロパティが自動的に絞り込まれます（TypeScript講座モジュール5の内容そのものです）。ReduxやZustandの設計思想もこの延長線上にあります。
🤔
なぜこうなるのか1つの状態に対して複数の更新パターンがあり、それぞれのロジックが絡み合っている場合、バラバラのuseStateとその場しのぎの更新処理で管理すると、「どの操作がどのstateにどう影響するか」を追うのが難しくなります。useReducerは「起こりうる操作(アクション)の種類」と「それぞれの結果」を1つの関数に集約するので、状態がどう変化するかを1箇所読むだけで把握できるようになります。
🥤
たとえ話自動販売機を思い浮かべてください。「コーラのボタンを押す」「お茶のボタンを押す」「お釣りボタンを押す」など、いろんな操作がありますが、実際に中で何が起こるかを決めているのは、自動販売機の中にある1つの制御装置(reducer)です。ボタン(アクション)がたくさんあっても、「何が起きるか」を決める場所が1箇所にまとまっていれば、もし変な動きをしたときも、直すべき場所がすぐに分かります。

応用

解答例を見る 
type Todo = { id: number; text: string; done: boolean };

type TodoAction =
  | { type: "ADD"; text: string }
  | { type: "TOGGLE"; id: number }
  | { type: "REMOVE"; id: number };

let nextId = 1;

function todoReducer(state: Todo[], action: TodoAction): Todo[] {
  switch (action.type) {
    case "ADD":
      return [...state, { id: nextId++, text: action.text, done: false }];
    case "TOGGLE":
      return state.map((t) =>
        t.id === action.id ? { ...t, done: !t.done } : t
      );
    case "REMOVE":
      return state.filter((t) => t.id !== action.id);
  }
}

4-2. Context APIと状態のリフトアップ

props経由でデータを何段も下に渡し続ける「プロップドリリング」がつらくなったら、Context APIの出番です。ただしすべての状態をContextにするのはアンチパターンで、Contextの値が変わるたびに、それを購読するすべてのコンポーネントが再レンダリングされることを理解しておく必要があります。

ThemeContext.tsx
type Theme = "light" | "dark";
type ThemeContextValue = { theme: Theme; toggleTheme: () => void };

const ThemeContext = createContext<ThemeContextValue | null>(null);

function ThemeProvider({ children }: { children: React.ReactNode }) {
  const [theme, setTheme] = useState<Theme>("light");

  const toggleTheme = useCallback(() => {
    setTheme((t) => (t === "light" ? "dark" : "light"));
  }, []);

  const value = useMemo(() => ({ theme, toggleTheme }), [theme, toggleTheme]);

  return <ThemeContext.Provider value={value}>{children}</ThemeContext.Provider>;
}

// 使う側専用のカスタムフックにしておくと、nullチェックを毎回書かずに済む
function useTheme() {
  const ctx = useContext(ThemeContext);
  if (!ctx) throw new Error("useTheme must be used within ThemeProvider");
  return ctx;
}
⚠️
やりがちなミスvalue={{ theme, toggleTheme }}のようにインラインでオブジェクトを作ると、Providerが再レンダリングされるたびに新しい参照が生成され、Contextを購読する全コンポーネントが不要に再レンダリングされます。useMemoで安定させましょう。
🤔
なぜこうなるのかpropsを何段も下のコンポーネントへ渡し続けると、途中のコンポーネントは自分では使わない値をただ中継するためだけに受け取ることになり、コードの見通しが悪くなります(プロップドリリング)。Contextは「木構造のどの深さからでも直接値を取り出せる棚」を用意する仕組みです。ただしContextの値が変わるたびに、それを購読しているコンポーネント全部が再レンダリングされるため、「本当に広い範囲で必要な値」だけに使うべきで、何でもかんでもContext化すると、逆に再レンダリングのコストが増えてしまいます。
📌
たとえ話教室の一番後ろの席の子にプリントを配るのに、前から1人ずつ手渡しでリレーしていくと(プロップドリリング)、途中の全員がプリントを一瞬持つことになり、時間もかかります。それより「掲示板」に貼っておいて、必要な子がいつでも見に行けるようにする(Context)ほうが早いですよね。でも、掲示板の内容を変えるたびに「クラス全員が確認しに行かないといけない」としたら、それはそれで大変です。だから本当にクラス全体で必要な情報だけを掲示板に貼るべきなのです。

フォームとバリデーション実務パターン

5-1. 制御コンポーネントとバリデーション設計

フォームの値をstateで管理する「制御コンポーネント」が基本です。バリデーションは「入力のたびに実行する」か「送信時にまとめて実行する」かで、ユーザー体験が大きく変わります。実務では両方を組み合わせることが多いです。

SignupForm.tsx
type FormValues = { email: string; password: string };
type FormErrors = Partial<Record<keyof FormValues, string>>;

function validate(values: FormValues): FormErrors {
  const errors: FormErrors = {};
  if (!values.email.includes("@")) {
    errors.email = "メールアドレスの形式が正しくありません";
  }
  if (values.password.length < 8) {
    errors.password = "パスワードは8文字以上で入力してください";
  }
  return errors;
}

function SignupForm() {
  const [values, setValues] = useState<FormValues>({ email: "", password: "" });
  const [touched, setTouched] = useState<Partial<Record<keyof FormValues, boolean>>>({});

  const errors = validate(values); // 送信前でも常に最新のエラーを計算しておく

  function handleBlur(field: keyof FormValues) {
    setTouched((prev) => ({ ...prev, [field]: true }));
  }

  return (
    <form>
      <input
        value={values.email}
        onChange={(e) => setValues((v) => ({ ...v, email: e.target.value }))}
        onBlur={() => handleBlur("email")}
      />
      {touched.email && errors.email && <p className="error">{errors.email}</p>}
    </form>
  );
}
💡
実務Tips入力した瞬間からエラーを表示すると「まだ何も入力していないのに赤字が出る」体験になりがちです。touched（そのフィールドを一度でも触ったか）を管理し、「touchedかつエラーがある場合だけ表示する」のが定番の折衷案です。
🤔
なぜこうなるのか入力欄を表示した瞬間からエラーを出してしまうと、ユーザーはまだ何も入力していないのに「間違っています」と怒られたような気持ちになります。touched(そのフィールドに一度でも触れたか)を記録しておき、「触ったあとにまだエラーがある場合だけ」表示することで、リアルタイムに間違いを教えてくれる親切さと、入力前から責められない心地よさを両立できます。
✏️
たとえ話先生が「まだノートに何も書いていないのに、赤ペンで『間違ってるよ』と印をつける」のは変ですよね。一度書いてみてから初めて添削するのが自然です。touchedは「その欄に一度でも手を付けたかどうか」を覚えておく付箋のようなもので、「触った後にまだ間違っている場合だけ」赤字を出すようにしているのです。

5-2. 送信状態管理とUXパターン

送信ボタンの連打による二重送信は実務で頻出のバグです。送信中は「送信中の状態」を持ち、ボタンを無効化するのが基本パターンです。また、送信失敗時にはユーザーが再入力せずに再送信できるよう、入力値を保持したままエラーだけを表示します。

type SubmitStatus = "idle" | "submitting" | "success" | "error";

function ContactForm() {
  const [status, setStatus] = useState<SubmitStatus>("idle");
  const [message, setMessage] = useState("");

  async function handleSubmit(e: React.FormEvent) {
    e.preventDefault();
    if (status === "submitting") return; // 二重送信防止

    setStatus("submitting");
    try {
      await postContact({ message });
      setStatus("success");
    } catch {
      setStatus("error");
    }
  }

  return (
    <form onSubmit={handleSubmit}>
      <textarea value={message} onChange={(e) => setMessage(e.target.value)} />
      <button type="submit" disabled={status === "submitting"}>
        {status === "submitting" ? "送信中..." : "送信する"}
      </button>
      {status === "error" && <p className="error">送信に失敗しました。もう一度お試しください</p>}
      {status === "success" && <p>送信しました！</p>}
    </form>
  );
}
⚠️
やりがちなミスdisabled属性だけに頼っていると、フォーム外からの二重送信（例えばEnterキー連打がイベントキューに溜まっている場合など）を防ぎきれないことがあります。handleSubmit関数の冒頭でも状態をチェックする「二重の防御」が安全です。
🤔
なぜこうなるのか送信ボタンを連打すると、サーバーに同じリクエストが複数回届き、二重登録や二重課金のようなバグにつながります。「今送信中かどうか」という状態を持ち、送信中はボタンを無効化しつつ、関数の内部でも二重にチェックすることで、見た目とロジックの両面から二重送信を防げます。楽観的UIは、サーバーの返事を待たずに先に見た目を変えることで体感速度を上げつつ、失敗したときは元に戻すことでユーザーに嘘をつかない設計です。
🍔
たとえ話レストランで注文ボタンを焦って何度も連打してしまうと、同じ料理が何皿も届いてしまうかもしれません(二重送信)。「ただいま注文を受け付けています、少々お待ちください」という札を出しておけば(送信中の状態でボタンを無効化)、間違えて連打しても追加注文にはなりません。楽観的UIは、「いいね」ボタンを押した瞬間にハートが赤くなる(サーバーの返事を待たずに先に見た目を変える)ようなもので、もし後で「実は失敗していました」と分かったら、こっそり元の色に戻すイメージです。
EX 5-2-a

いいねボタンの楽観的UIを実装する

応用

いいねボタンをクリックしたら即座に見た目を反映し（楽観的UI）、APIリクエストが失敗したら元の状態に戻すLikeButtonコンポーネントを実装してください。likeApi(): Promise<void>は失敗するとエラーをthrowするものとします。

解答例を見る 
function LikeButton() {
  const [liked, setLiked] = useState(false);

  async function handleClick() {
    const previous = liked;
    setLiked(!previous); // 先に見た目を反映（楽観的UI）

    try {
      await likeApi();
    } catch {
      setLiked(previous); // 失敗したら元に戻す
    }
  }

  return (
    <button onClick={handleClick}>
      {liked ? "♥ いいね済み" : "♡ いいね"}
    </button>
  );
}
EX 5-2-b

送信状態をuseReducerで管理する

発展

上記のSubmitStatus（"idle" | "submitting" | "success" | "error"）と、エラー時のメッセージを1つのuseReducerで管理するように書き換えてください。アクションは"SUBMIT_START"、"SUBMIT_SUCCESS"、{ type: "SUBMIT_ERROR"; message: string }とします。

解答例を見る 
type SubmitState = { status: SubmitStatus; errorMessage: string | null };
type SubmitAction =
  | { type: "SUBMIT_START" }
  | { type: "SUBMIT_SUCCESS" }
  | { type: "SUBMIT_ERROR"; message: string };

function submitReducer(state: SubmitState, action: SubmitAction): SubmitState {
  switch (action.type) {
    case "SUBMIT_START":
      return { status: "submitting", errorMessage: null };
    case "SUBMIT_SUCCESS":
      return { status: "success", errorMessage: null };
    case "SUBMIT_ERROR":
      return { status: "error", errorMessage: action.message };
  }
}

// 呼び出し側
const [state, dispatch] = useReducer(submitReducer, { status: "idle", errorMessage: null });

MODULE 06

実務でよく使う設計パターン

最後のモジュールは、ここまで学んだ内容を「コンポーネント設計」というより大きな視点にまとめます。

6-1. コンポーネント分割の考え方

「見た目（Presentational）」と「データ・ロジック（Container）」を分けて考えると、UIコンポーネントはテストしやすく、デザインの変更にも強くなります。近年はカスタムフックにロジックを寄せ、コンポーネント自体は見た目に専念させる形が主流です。

UserListContainer.tsx
// ロジック層: データ取得とビジネスロジックだけを担当
function useUserListPage() {
  const state = useFetch<User[]>("/api/users");
  const [keyword, setKeyword] = useState("");

  const filteredUsers =
    state.status === "success"
      ? state.data.filter((u) => u.name.includes(keyword))
      : [];

  return { state, keyword, setKeyword, filteredUsers };
}

// 見た目層: propsを受け取って表示するだけ（テストが書きやすい）
function UserListView({
  users,
  keyword,
  onKeywordChange,
}: {
  users: User[];
  keyword: string;
  onKeywordChange: (v: string) => void;
}) {
  return (
    <>
      <input value={keyword} onChange={(e) => onKeywordChange(e.target.value)} />
      <ul>{users.map((u) => <li key={u.id}>{u.name}</li>)}</ul>
    </>
  );
}

// 接続: 2つを組み合わせるだけの薄いコンポーネント
function UserListPage() {
  const { keyword, setKeyword, filteredUsers } = useUserListPage();
  return <UserListView users={filteredUsers} keyword={keyword} onKeywordChange={setKeyword} />;
}
💡
実務Tipsこの分割の一番のメリットは、UserListViewを単体でStorybookに表示したり、ロジックなしでスナップショットテストできる点です。「このコンポーネントをテストするのにAPIのモックが必要」と感じたら、分割のサインです。
🤔
なぜこうなるのかデータ取得とロジックを持つ部分と、見た目だけを担当する部分が1つのコンポーネントに混ざっていると、見た目を1つ変えたいだけなのに、通信処理やロジックまで気にしながらコードを読む必要が出てきます。分けておけば、見た目側はpropsさえ渡せばどんな状況でも表示を確認でき、テストやデザイン変更がしやすくなります。ロジック側をカスタムフックに切り出すことで、「このコンポーネントは何をするものか」を一言で説明できる粒度に保てます。
🍽️
たとえ話料理番組を思い浮かべてください。「食材を仕入れて下ごしらえする人」(ロジック・カスタムフック)と、「お皿に盛り付けて見た目よく提供する人」(見た目のコンポーネント)が分かれていると、盛り付けだけ変えたいときは盛り付け担当だけに相談すればよく、食材の仕入れ担当に迷惑をかけません。1人が全部やろうとすると、盛り付けを少し変えたいだけなのに、仕入れの手順まで気にしないといけなくなってしまいます。
EX 6-1-a

ロジックと見た目を分離する

応用

次のProductCardは、データ取得と表示が1つのコンポーネントに混ざっています。useProductCard(productId)カスタムフック（ロジック）と、propsだけを受け取るProductCardView（見た目）に分割してください。

function ProductCard({ productId }: { productId: number }) {
  const [product, setProduct] = useState<Product | null>(null);

  useEffect(() => {
    fetchProduct(productId).then(setProduct);
  }, [productId]);

  if (!product) return <p>読み込み中...</p>;
  return <div>{product.name} - {product.price}円</div>;
}
解答例を見る 
function useProductCard(productId: number) {
  const [product, setProduct] = useState<Product | null>(null);

  useEffect(() => {
    fetchProduct(productId).then(setProduct);
  }, [productId]);

  return { product };
}

function ProductCardView({ product }: { product: Product | null }) {
  if (!product) return <p>読み込み中...</p>;
  return <div>{product.name} - {product.price}円</div>;
}

function ProductCard({ productId }: { productId: number }) {
  const { product } = useProductCard(productId);
  return <ProductCardView product={product} />;
}

コンポーネント分割の基準を説明する

基礎確認

「1つのコンポーネントを分割すべきタイミング」を、JSXの行数以外の観点から2つ挙げて説明してください。

解答例を見る

例1: 「このコンポーネントは何をするものですか」と一言で説明できなくなったとき（複数の責任を持ち始めているサイン）。例2: 同じUIパターン（カード、リストアイテムなど）を別の場所でコピペし始めたとき（再利用可能な単位として切り出すべきサイン）。他にも「テストしようとするとモックすべき依存が増えすぎる」なども有効な基準です。

6-2. エラーバウンダリと非同期データの表示パターン

子コンポーネントで発生した予期しないレンダリングエラーは、そのままだとアプリ全体が白画面になります。ErrorBoundary（現状クラスコンポーネントでのみ実装可能）で囲むことで、一部分だけをフォールバックUIに差し替えられます。

ErrorBoundary.tsx
type Props = { children: React.ReactNode; fallback: React.ReactNode };
type State = { hasError: boolean };

class ErrorBoundary extends React.Component<Props, State> {
  state: State = { hasError: false };

  static getDerivedStateFromError(): State {
    return { hasError: true };
  }

  componentDidCatch(error: Error, info: React.ErrorInfo) {
    console.error("caught by ErrorBoundary:", error, info);
  }

  render() {
    if (this.state.hasError) {
      return this.props.fallback;
    }
    return this.props.children;
  }
}

// 使う側: 一部分だけをエラーバウンダリで囲む
function Dashboard() {
  return (
    <>
      <Header />
      <ErrorBoundary fallback={<p>このウィジェットの表示に失敗しました</p>}>
        <RiskyWidget />
      </ErrorBoundary>
    </>
  );
}
⚠️
やりがちなミスErrorBoundaryはレンダリング中の例外しか捕まえられません。イベントハンドラ内の例外（onClickなど）やasync処理中の例外は捕まえられないため、それらは通常のtry/catchで扱う必要があります。
🤔
なぜこうなるのか1つの小さな部品(ウィジェット)がエラーを起こしただけで、アプリ全体が真っ白な画面になってしまうのは、体験として最悪です。ErrorBoundaryで「壊れてもよい範囲」をあらかじめ区切っておくことで、被害をその部分だけに閉じ込め、それ以外の部分は問題なく動き続けられます。もしアプリ全体を1つのErrorBoundaryで囲んだだけだと、結局「1箇所の不具合で全部道連れ」というリスクは残ったままです。
💡
たとえ話家の電気のブレーカーを思い浮かべてください。もし家全体に1つのブレーカーしかなかったら、キッチンの電子レンジがショートしただけで家中の電気が消えてしまいます。でも部屋ごとにブレーカーが分かれていれば、キッチンの電気だけが落ちて、リビングや寝室の電気はちゃんと点いたままです。ウィジェットごとにErrorBoundaryを用意するのは、まさにこの「部屋ごとのブレーカー」と同じ考え方です。
EX 6-2-a

アプリ全体を1つのErrorBoundaryで囲む

基礎確認

上記のErrorBoundaryを使って、アプリのルート（<App />相当）全体を、「予期しないエラーが発生しました。ページを再読み込みしてください」というフォールバックで囲むコードを書いてください。

解答例を見る

  return (
    <ErrorBoundary fallback={<p>予期しないエラーが発生しました。ページを再読み込みしてください</p>}>
      <App />
    </ErrorBoundary>
  );
}
EX 6-2-b

複数のウィジェットを個別のErrorBoundaryで守る

応用

WeatherWidgetとNewsWidgetという2つの独立したウィジェットがあるダッシュボードで、片方がクラッシュしてももう片方は表示され続けるように、それぞれを個別のErrorBoundaryで囲んでください。全体を1つのErrorBoundaryで囲む場合と比べて、何が改善されるか一言で説明してください。

解答例を見る 
function Dashboard() {
  return (
    <>
      <ErrorBoundary fallback={<p>天気の取得に失敗しました</p>}>
        <WeatherWidget />
      </ErrorBoundary>
      <ErrorBoundary fallback={<p>ニュースの取得に失敗しました</p>}>
        <NewsWidget />
      </ErrorBoundary>
    </>
  );
}

改善点: エラーの影響範囲を最小化できます。全体を1つのErrorBoundaryで囲むと、NewsWidgetのバグでWeatherWidgetまで巻き添えで消えてしまいますが、個別に分ければ被害をそのウィジェットだけに閉じ込められます。
